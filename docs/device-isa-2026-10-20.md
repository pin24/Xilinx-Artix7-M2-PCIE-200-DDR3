# DEVICE-ISA — device-side ISA для программы на FPGA tdot (2026-10-20)

> Черновик. Описывает БИТОВЫЙ формат программы, host-протокол запуска и семантику
> интерпретатора. Линия проекта: host гонит каждый dot через PCIe-IOCTL (~15 мс,
> BUG-071) — fix по openTPU: программа живёт в DRAM, host шлёт ARG0..ARG7 + один RUN,
> устройство само крутит линейную цепочку юнитов (вложенные LOOP <=4) и пишет одно
> status-слово в completion-mailbox (WAITW-аналог).
>
> Файлы модели: `data/device_isa.py` (битовый компилятор + numpy-интерпретатор),
> `data/devseq.py` (функциональная модель «данные+программа», эталон семантики),
> `data/test_device_isa.py` (тесты). Смежное: `docs/device-prog-2026-10-20.md`.

---

## 1. Цели и границы

- **Не трогаем** существующий per-dot путь (микрокод tdot ядра и регистры планировщика
  `SCHED_*`, §3/§3.1 ADDRESS_MAP) — это отдельные механизмы. Данная ISA — ПРОГРАММА
  **поверх** ring: хостовый интерпретатор, который формирует один большой набор dot-задач
  и ждёт одно завершение.
- Устройство держит **веса модели резидентными** в DDR3 (бюджет 256 МБ, см.
  device-prog §3a). Батч данных — один DMA.
- Принцип «каждое движение данных — явно» (device-prog §5): хост читает только
  результат батча и одно status-слово; внутри программы никакого host-чтения.

## 2. Формат программы — таблица юнитов в DRAM

Программа = **массив 32-байтных юнитов** в DDR3 (little-endian), по адресу
`ARG[PROG_REG]`. Количество юнитов = размер_программы / 32 (граница задаётся
каталогом/концом региона; в модели — длиной байтового блока).

Каждый юнит — 8 × 32-битных слов (ровно как дескрипторы планировщика, 32 Б):

| Слово | Биты | Поле | Описание |
|---|---|---|---|
| W0 | `[15:0]` | `n_in`  | Размерность входа (кол-во нейронов предыдущего слоя / признаков) |
| W0 | `[31:16]` | `n_out` | Размерность выхода |
| W1 | `[7:0]`  | `pass`  | Сколько раз прогнать ЧЕРЕЗ этот слой (LOOP, 1..255; 0→1) |
| W1 | `[8]`    | `relu`  | 1 = ReLU после каждого прохода слоя |
| W1 | `[9]`    | `b_en`  | 1 = добавлять bias (из b-адреса); 0 = без bias |
| W1 | `[10]`   | `src`   | 0 = data (вход автономного батча), 1 = prev (выход предыдущего юнита) |
| W1 | `[15:11]`| резерв  | 0 |
| W1 | `[31:16]`| `tag`   | 16-бит тег юнита (маркировка; в модели — ключ к весам) |
| W2 | `[3:0]`  | `w_reg` | выбор ARG-регистра для весов (0..7) |
| W2 | `[31:4]` | `w_imm` | 28-бит смещение: `w_addr = ARG[w_reg] + w_imm` |
| W3 | `[3:0]`  | `b_reg` | выбор ARG-регистра для bias |
| W3 | `[31:4]` | `b_imm` | `b_addr = ARG[b_reg] + b_imm` |
| W4 | `[3:0]`  | `o_reg` | выбор ARG-регистра для вывода |
| W4 | `[31:4]` | `o_imm` | `out_addr = ARG[o_reg] + o_imm` |
| W5..W7 | — | резерв | 0 (пространство под будущие RTL-опции) |

Адрес всегда = `ARG[x] + imm` — «R[x]+imm» дисциплина. `imm` 28 бит покрывает
весь 256 МБ DDR3 (offset от `0x80000000`).

## 3. Host-протокол: ARG0..ARG7 + RUN

По openTPU: хост пишет до запуска ARG-регистры один раз, затем **один** RUN.

| ARG | Назначение по умолчанию | Значение (смещения §6 ADDRESS_MAP) |
|---|---|---|
| ARG0 | `PROG` — база таблицы программы | `0x0010_0000` |
| ARG1 | `DATA` — база входного батча | `0x0020_0000` |
| ARG2 | `RESULT` — база результатов | `0x00A0_0000` |
| ARG3 | `WEIGHTS` — база резидентных весов | `0x0060_0000` |
| ARG4 | `COMP` — completion-mailbox (одно слово) | `0x0011_0000` |
| ARG5 | `LOOP` — свободный (внешний счётчик LOOP) | `0` |
| ARG6,7 | свободные | `0` |

- `RUN` — одиночный регистр (самосброс импульс). Запуск идемпотентен: новое вычисление
  начинается только по новому RUN.
- Устройство само крутит программу: выбирает юниты, формирует dot-задачи (линейный слой =
  per-output-neuron dot), ждёт кольцо, пишет результат в `out_addr`, переходит к следующему.
- **LOOP-семантика (вложенность <=4):** `RUN` запускает программу; LOOP повторяет
  ПОДПРОГРАММУ N раз.
  - Уровень 1 (внутренний): `pass` юнита — повтор слоя через СЕБЯ N раз (выход прохода p —
    вход прохода p+1; требует `n_in == n_out`, если `pass > 1`).
  - Уровень 2 (внешний, на границе батча): программа применяется целиком `repeat` раз,
    вывод прохода r — вход прохода r+1 (рекуррентный буфер) — управляется `args['repeat']`
    (прокси для ARG5 LOOP).
  - Глубже — композиция: юнит с `src=prev` и повторные юниты образуют цепочку вложенных
    циклов; модель исполняет без жёсткого лимита, RTL обязан ограничивать глубину <=4
    (эмулируемая глубина модели — количество одновременно активных LOOP x слоёв).
  - Итоговое значение для RTL: рационально держать не более 4 вложенных циклов (ядро
    интерпретатора + 3 внешних), см. §5.3.

## 4. WAITW-mailbox: completion

- В КОНЦЕ программы устройство пишет **одно 32-битное status-слово** по адресу
  `ARG[COMP_REG]` (= `0x0011_0000` по умолчанию). Хост читает ОДНО слово (WAITW-аналог).
- Формат статуса: бит0 = `DONE` (1=OK); биты[31:1] зарезервированы (в модели — полное
  слово по умолчанию `0x00000001`, переопределяется `args['status']`).
- Ошибка интерпретации — отдельное слово (`STATUS_ERR`, reserved), по факту не пишется
  в валидных программах.

## 5. Семантика интерпретатора (numpy-модель)

Точная модель — `data/device_isa.py`. Устройственное ядро здесь СЕМАНТИЧЕСКИ:
линейный слой = `linear_pass`: `out = cur @ W (+b)` (опц. ReLU), как devseq/nn_audio_common.

Для каждого юнита (в порядке следования):
1. `W = weights[tag]` — веса/смещение модели (резидентные).
2. Если `pass > 1` и `n_in != n_out` — ошибка (неквадратный слой нельзя повторять).
3. `w_addr/b_addr/out_addr` — вычисляются как `ARG[reg] + imm` (адреса в DRAM; в
   numpy-модели данные/веса передаются объектами, адреса идут в trace).
4. LOOP по `pass`: `x₀` = (датчик входа): если `src=data` → вход батча, иначе выход
   предыдущего юнита; `xₚ = linear_pass(x{p-1}, W, b если b_en, relu)`.
5. Результат юнита — следующий вход цепочки `cur`.

Программа целиком (`repeat` раз, LOOP уровня 2): `cur` стартует с входного батча,
каждый проход — прогон всей цепочки с подачей выхода в начало.

Возвраты модели:
- `run_program(data, program, weights, args) -> result` — результат батча `(B, out_last)`.
- `run_program_trace(...) -> (result, trace)` — плюс разрешённые адреса (для RTL-сверки).
- `run_program_mb(...) -> (result, completion)` — completion-mailbox семантика:
  `completion = {'addr', 'word'}` — куда и какое status-слово устройство напишет.
- `bits(unit)->bytes`, `parse(bytes)->[units]`, `compile_program(units)->bytes` — битовый
  компилятор/разборщик (LE). `make_unit(...)` — конструктор юнита.

`weights` — `{tag: (W, b)}` (numpy float32); общий `tag` у двух юнитов = общие веса
(полезно для рекуррентных циклов). `args` — `{ARG-reg: значение}` + служебные
`'repeat'` (внешний LOOP), `'status'` (значение status-слова), `'comp_reg'`.

## 6. Тесты

`data/test_device_isa.py` (pytest-совместимые assertions; запуск `python data/test_device_isa.py`):

1. **roundtrip**: `bits()` ↔ `parse_unit()` не теряет поля; `compile_program(parse(b)) == b`.
2. **Программа `[W1(relu), W2]` == `nn_audio_common.forward_batch` (cpu)** — и список юнитов,
   и байтовую форму: max|diff| < 1e-6.
3. **LOOP на квадратном слое**: юнит `pass=N` == применить слой N раз; `args['repeat']` ==
   применить цепочку N раз (как devseq).
4. **completion-mailbox**: программируемый адрес/значение status-слова.
