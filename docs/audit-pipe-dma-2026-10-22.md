# Аудит host-обвязки: 8 MiB-чанк + конвейерный двойной буфер (BUG-071)

Дата: 2026-10-22
Объект: proposal снижения ~15 мс/IOCTL `XdmaWinDma` (BUG-071)
Аудитор: MultiTool (инженер-аудитор host-обвязки)
Режим: read-only (ничего не изменено; создан только этот отчёт)
Целевой репозиторий: `C:\A7_M2\Xilinx-Artix7-M2-PCIE-200-DDR3`

---

## 0. Кратко

Предлагаемые изменения:
1. `DMA_CHUNK`: 1 MiB → 8 MiB (`test_dma_win.py`, дублируется в `xdma_driver.py`).
2. Async-конвейер с 2 OVERLAPPED + 2 event в `write_dma`/`read_dma`.

**Итоговый вердикт:**
- **(a) 8 MiB — допустимо по лимитам драйвера**, но выигрыш косметический для реальной нагрузки (RTL-контракт позволяет, single-packet, дескрипторный банк хватает). Риск/выгода неоптимальны: для типовых батчей обучение/ring (КБ…МБ) число вызовов не уменьшается, а ростовой ROF/0x124-риск от больших транзакций остаётся.
- **(b) Двойной буфер на одном канале — бесполезен**: per-engine WDF-очередь `WdfIoQueueDispatchSequential` (`dma_driver.c:357`) сериализует все запросы канала; второй `WriteFile(h2c_0)` встаёт в хвост, пока первый (с его bounded-poll ~10 c) не завершится. Реальное перекрытие — только cross-channel h2c↔c2h (разные движки, разные транзакции), и оно уже поддерживается драйвером без P3-пула.
- **(c) Общий `self._ev` + двойной буфер — RISK**: один manual-reset event нельзя использовать для двух одновременных ожиданий (ResetEvent перед вторым `_xfer` затопчет первое). На одном канале это не проявится (b), но для cross-channel конвейера нужен **отдельный event на каждый in-flight OVERLAPPED**; структуры/буферы должны жить до завершения. Регистровые `read()` (`\user`) НЕ ломаются конвейером: default-очередь освобождается после forward в engine-очередь, т.е. регистровый доступ выполняется независимо от in-flight DMA.
- **(d) Таймаут/отмена**: current `_xfer` (10 с + raise) при его расширении в конвейер требует `CancelIoEx` + аккуратный сброс; канал зажат на ~10 с одним зависшим запросом (bounded-poll в `EvtIoWriteDma`/`EvtIoReadDma`), так что конвейер лишь умножает число застрявших IRP. Фиксы BUG-072/073 в ядре (корректное завершение + cancel∩timeout) уже заземлены, но они не делают последовательный канал «быстрым».
- **(e) Не внедрять сейчас**: первый приоритет — снижение числа host-вызовов (device_prog-программа в DRAM, packed-submit), а не размер чанка/конвейер. Если и делать pipelining — только cross-channel h2c↔c2h и только после включения P3-пула транзакций/дескрипторов.

## 3. Рекомендация

### Что внедрять (приоритет — не размер чанка, а число вызовов)

1. **НЕ увеличивать `DMA_CHUNK` до 8 MiB** для повседневной нагрузки:
   - Для типовых операций (dot, веса, результаты — КБ…МБ) 8 MiB не уменьшает число `_xfer`-вызовов (один запрос уже < 1 MiB), а добавляет ROF-риск (`file_io.c:722`).
   - Оставить `DMA_CHUNK = 1 MiB` как проверенный дефолт. Опционально — **параметр** (не константа) и переключение на 8 MiB «только для больших bulk-переносов» с предупреждением о ROF, под стендовый A/B. Это самый безопасный путь, если 8 MiB понадобится: предел драйвера позволяет, остальные проверки OK.

2. **НЕ добавлять двойной буфер на одном канале** — это противоречит аппарату/драйверу:
   - per-engine queue Sequential (`dma_driver.c:357`) + один `dmaTransaction` на движок ⇒ второй `WriteFile(h2c_0)` не перекроется. Бессмысленно и рискованно.

3. **Реальное перекрытие — только h2c↔c2h** и оно уже возможно без P3:
   - Разные движки/транзакции, разные engine-очереди. Можно «шлём следующий батч (h2c), пока читаем результат (c2h)». Это единственный кандидат на конвейер, и его стоит проектировать отдельно с **event-per-channel**.

4. **Более высокая отдача — снижение числа host-вызовов, а не конвейер на фиксированных вызовах:**
   - device_prog-программа в DRAM (`docs/device-isa-2026-10-20.md`) — хост шлёт ARG0..7 + RUN вместо многих IOCTL; это прямой fix BUG-071.
   - packed-submit (минимум вызовов) — уже в работе (`docs/ERROR_HISTORY.md:846`).

### Дефолт (если всё же делать)

- `DMA_CHUNK` — оставить 1 MiB; при желании 8 MiB — opt-in параметр + стендовый A/B под ROF.
- Конвейер — **отложить**; когда делать — только cross-channel h2c↔c2h, с отдельными `_ev` на канал, `CancelIoEx` на timeout, lifetime-массивом OVERLAPPED/buffer.

## 4. Что не проверено (лимиты и открытые вопросы)

- **Стендовый замер ROF/0x124 при 8 MiB** — на железе не запускалось (read-only). Главный открытый риск для (a).
- **Поведение default-очереди при forwarding** — по документации KMDF, forward освобождает default-очередь; комментарий `dma_driver.c:335` (заявляет «Parallel») расходится с фактическим `WdfIoQueueDispatchSequential` (`:357`) — комментарий устарел/ошибочен; подтверждение на стенде не делалось.
- **Точный профиль 15 мс** — BUG-071 трактуется как per-call latency малой MDL-транзакции; разбивка «где именно» (WDF-инициализация vs MDL pin vs событие) не снималась.
- **P3-пул** — код-путей на транзакции/дескрипторы нет; не проверялся на железе.
- **Реальный размер типовых батчей** обучение/ring — оценён по коду (КБ…МБ), калибровочного лога по размеру/числу вызовов не найдено.
- **`CancelIoEx` host-путь** — не замерен (перекрытие/сброс очереди при timeout на конвейере).
- **Multi-node открытие** h2c_0+h2c_bram_0 может переопределить `translateAxiBase` глобально (`file_io.c:186‑193`) — при конвейере на канале это взаимодействие не проверено.
