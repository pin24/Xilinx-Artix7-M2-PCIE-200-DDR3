## 2. Механика h2c на драйверной стороне

### 2.1 Дескрипторная цепочка для юзерского буфера большого объёма

`XDMA_EngineProgramDma` (dma_engine.c:898–1117) строит ОДНУ цепочку из SG-элементов:

- Каждый SG-элемент (MDL-страница, гранулярность 4 КБ) режется на срезы по `XDMA_DESC_MAX_BYTES = 8192 Б` (dma_engine.c:981, 1013–1017).
- Счётчик дескрипторов: `total += ceil(len/8192)` (dma_engine.c:980–983).
- Банк дескрипторов: `XDMA_MAX_DESC_COUNT * sizeof(DMA_DESCRIPTOR) + 1 spare = 2048*32+32 = 65568 Б` (dma_engine.c:75, dma_engine.h:47).
- Клэмп при `total > descBankLens` (dma_engine.c:985–1000) — жёсткая защита, но для 500 КБ **недостижим**.

**Счёт для 500 КБ:** worst case = одна 4-КБ MDL-страница на дескриптор → `500 КБ / 4 КБ ≈ 125–128` дескрипторов. Лимит 2048. Банк — **не узкое место**, клэмп не срабатывает. Хвостовой счётчик `progBytes<reqBytes` (dma_engine.c:1064) не зажжётся.

**Вывод по τ.1:** дескрипторная логика корректна для 500 КБ; банка хватает; «тихое» обрезание хвоста исключено.

### 2.2 Один WDF-пакет vs multi-packet

- `WdfDmaTransactionSetMaximumLength(..., XDMA_MAX_TRANSFER_SIZE=8 МБ)` (file_io.c:724, dma_engine.h:32) → весь IRP до 8 МБ — **один** WDF-пакет.
- Host режет запись на `DMA_CHUNK = 1 МиБ` (test_dma_win.py:73), т.е. 500 КБ — ровно 1 пакет, 1 ProgramDma.
- `XDMA_MAX_WDF_PACKETS=16` (dma_engine.h:55) и цикл «ждать пакет за пакетом» (file_io.c:759–827) — защита от IRP > 8 МБ. Для 500 КБ цикл выполняется **один раз**; multi-packet путь (BUG-053/E-19, file_io.c:717–723) тут **не задействуется**.

**Вывод по τ.2:** зависание НЕ связано с перезапуском пакетов. Здесь ровно один EngineStart на одну цепочку.

### 2.3 `XDMA_EngineWaitCompletion` — почему BUSY-рассинхронизация невосстановима

Пулл (dma_engine.c:1553–1647):
```
read completedDescCount; statusRC (read-clear); hwDone = !(statusRC & BUSY);
if (hwDone && actual >= expected) { EngineProcessTransfer; SUCCESS; }
```
Таймаут через ~10 с: `EngineStop` (dma_engine.c:1154, только RUN=0) + CAS `txnDone` + возврат `STATUS_TIMEOUT` (dma_engine.c:1641–1644).

КРИТИЧНО для «невосстановимости»:
1. `EngineStop` снимает **только бит RUN (bit0)** через controlW1C (dma_engine.c:1155). Он **не** сбрасывает внутренний FSM/состояние DMA-инга, не гасит зависший хвост burst в SmartConnect/MIG.
2. `XDMA_EngineResetIdle` (dma_engine.c:1160–1183) = то же самое + read-clear statusRC + пере-привязка firstDesc. **Это НЕ аппаратный reset канала**, это «мягкий idle»: если BUSY держится из-за незавершённого транзакта на шине (AXI-slave не вернул BLAST/BVALID), статус RC вернёт BUSY снова в тот же момент, и движок сразу застревает опять.
3. Следующий `write_dma` даже 4 КБ: `XDMA_EngineResetIdle` (dma_engine.c:1100) пере-ставит firstDesc и `EngineStart` (dma_engine.c:1112) выставит RUN → движок пытается идти туда же, где застрял хвост burst → снова wait forever → `statusRC` снова BUSY. **Аппаратно движок не может завершить ни один дескриптор**, потому что его M_AXI не может продвинуть зависший write.**BUSY — это НЕ просто флаг, это застрявший FSM на границе PCIe→AXI.**

**Вывод по τ.3:** критерий `hwDone && actual>=expected` при BUSY-веодже никогда не станет истинным; таймаут формально снимает host-очередь (фикс BUG-072/073 работает — запрос не виснет), но движок остаётся BUSY, т.е. «скрытый клин» сохраняется на аппаратном уровне.

### 2.4 Реального аппаратного reset канала в драйвере НЕТ

Проверено по всему дереву драйвера:
- `XDMA_CTRL_RST (BIT31)` объявлен в reg.h:74, но **нигде не используется**. Все пути пишут только RUN (bit0)/IE/POLL через controlW1S/W1C.
- SGDMA COMMON block mapped (device.c:227–228, `sgdmaRegs`=0x6000), но код пишет туда **только** `creditModeEnableW1S` для streaming C2H-ринга (dma_engine.c:798). Глобальный `control/controlW1S` блока (reg.h:202–212) — НЕ трогается.
- `EngineStop` + `XDMA_EngineResetIdle` (см. §2.3) — soft-idle, не reset.
- `XDMA_DeviceClose` (device.c:343) — тоже только EngineStop.
- Нет никакого WdfDmaEnabler-level «reset adapter», нет дёргания `sys_rst_n`/`axi_aresetn` из драйвера.
- **После прошивки** единственный способ снять BUSY — PCIe-направленный reset или power-cycle FPGA (это пере-триггерит `sys_rst_n` и проп. домен XDMA).

**Вывод по τ.4:** в драйвере отсутствует программный сброс канала, способный выбить BUSY из зависшего write-FSM. Таймаут-путь (EngineStop+Complete) гасит только host-очередь, а не аппаратный движок — поэтому «timeout-восстановление» невозможно.

### 2.5 Путь host-h2c → DDR3 и роль MIG/SMC

Топология (scripts/xdma_ddr3_bd.tcl, flat):
```
xdma_0.M_AXI ── xdma_axi_smc/S00_AXI ──┐
xdma_axi_smc: 4 SI (S00=XDMA M_AXI, S01=MM2S-DM,
                     S02=S2MM-DM, S03=M_AXI_TDOT) → 2 MI (M00=MIG, M01=diag_bram)
mig_7series_0/S_AXI  (M00)
```
- MIG: AXI4, `C0_S_AXI_DATA_WIDTH=128`, `ADDR_WIDTH=28`, `ID_WIDTH=5`, `NARROW_BURST=0`, `C0_C_RD_WR_ARB_ALGORITHM=RD_PRI_REG` (read-приоритет).
- SMC имеет 3 часовых домена: aclk (PCIe/XDMA axi_aclk), aclk1 (MIG ui_clk 100 МГц), aclk2 (fabric 125 МГц) (xdma_ddr3_bd.tcl:495–496; dfx:724–740).
- Адресация: драйвер добавляет базу `XDMA_DDR3_AXI_BASE=0x80000000` (reg.h:59, dma_engine.c:935), MIG замаплен по 0x80000000 range 0x10000000 (xdma_ddr3_bd.tcl:903).

**Почему большой burst «шьёт» выход, а 64 Б проходит:**
- 64 Б — 1–2 коротких транзакта; даже при RD_PRI_REG бизнес за окно не переполняется.
- 500 КБ — поток posted write из одного S-порта в один M-порт MIG. Арбитр MIG `RD_PRI_REG` отдаёт приоритет чтению, поэтому на фоне активных чтений tdot/задач длинные записи задерживаются в SMC. При единственном мастере это мертвец: SMC-кроссбар ждёт BLAST/BVALID от MIG, а MIG не может его дать, пока не обслужил долгие очереди записи → head-of-line blocking. **Один висящий write транзакт = весь канал упёрт**, SMC не имеет per-транзактного timeout на стороне S (это не программа, а FIFO+арбитр).

**Вывод по τ.5 (secondary/plausible):** переполнение/застрявший posted-write в SMC/MIG — **наиболее вероятный спусковой механизм** зависания именно при большом объёме. Малый объём не достигает точки насыщения. Это согласуется с тем, что RTL-сторожевые SMC отсутствуют, а AXI-Lite (другой SMC `xdma_axi_lite_smc`, отдельный домен) жив — поэтому MAGIC/CORE_PARAMS читаются, а M_AXI (данные) — мёртв.

### 2.6 Невыравненность и SGDMA

- `XdmaWinDma.write_dma` требует `align != 4` для адреса и 4-байтового выравнивания буфера (test_dma_win.py:64, 177–183).
- `DescriptorIsAligned` (dma_engine.c:612) в Contiguous-режиме проверяет `dstAddrLo % alignAddr`, `numBytes % alignLength`, `srcAddrLo % alignAddr`; alignAddr/alignLength = 256 Б (по умолчанию FIX-ROF, dma_engine.c:861–862).
- CARD-адрес: `0x80000000 + 0x200000 = 0x80200000` — кратен 256 и 4 КБ. host-буфер chunk'ов 1 МиБ обычно 4-КБ-выровнен (это не гарантируется, но 500-КБ запись проходит как единый контигуированный буфер, см. ring_check — numpy array; WDF построит MDL из смежных страниц, если буфер контигуированный).
- **Если** буфер не 4-КБ-выровнен, элементы не кратны 256 → `DescriptorIsAligned` вернёт FALSE → только warning (dma_engine.c:1051–1053), **запись не отклоняется**. Для SGDMA это допустимо при 64-бит MM (требуется выравнивание по datapath, но не жёстко 4КБ).

**Вывод по τ.6 (low):** для 500-КБ записи в 0x200000 невыравненность не является причиной клина: адрес кратен 4КБ, размер контигуированный. Даже если бы был misalign — он породил бы только warning, а не аппаратный BUSY.

## 4. Ответ на центральный вопрос

> **Почему при БОЛЬШОМ объёме движок виснет, а при 64 Б — нет, и почему не восстанавливается программно?**

**Почему большой объём виснет:**
h2c-движок шлёт поток posted-write из XDMA `M_AXI` через единый SmartConnect `xdma_axi_smc` (S00) к единственному слейву MIG. При 500 КБ SMC/MIG не справляются с длинным потоком под арбитром `RD_PRI_REG` (приоритет чтения) и на фоне чтений tdot/задач: один транзакт записи застревает в head-of-line, MIG не отдаёт BLAST/BVALID, SMC ждёт вечно. Движок h2c не получает завершения дескриптора → остаётся BUSY навсегда. При 64 Б поток на 3-4 порядка меньше, не достигает насыщения, транзакты завершаются — движок переиспользуется.

**Почему 4 КБ после клина тоже виснет:**
движок в BUSY пытается продвинуть тот же застрявший хвост по тому же адресу; т.к. `XDMA_EngineResetIdle`/`EngineStart` пере-привязывают firstDesc на тот же банк/адрес, новый старт упирается в тот же застрявший write → вечный вейт. AXI-Lite жив потому, что это **отдельный** SMC (`xdma_axi_lite_smc`, домен периферии) и отдельный M_AXI_LITE мастер — он не делит канал данных с M_AXI.

**Почему не восстанавливается программно:**
в драйвере **отсутствует аппаратный сброс канала**: `XDMA_CTRL_RST(bit31)` объявлен, но не используется; global `SGDMA_COMMON.control` не пишется; `EngineStop` и `XDMA_EngineResetIdle` — это только `RUN=0` + read-clear `statusRC` + перепривязка `firstDesc`, они НЕ выбивают BUSY из застрявшего FSM и НЕ сбрасывают SMC/MIG. Таймаут снимает host-очередь (фикс BUG-072/073), но оставляет движок BUSY. Единственный путь — сброс по питанию/`sys_rst_n` (power-cycle/reboot), который пере-триггерит все домены XDMA и SMC/MIG. RTL-сторожевые tdot не помогают, т.к. живут в другом мастере (ядро tdot), а не в пути XDMA h2c.

## 5. Корневая причина (Итог)

1. **Триггер (confirmed):** большой h2c posted-write (500 КБ) насыщает единственный SMC→MIG путь; застрявший write-транзакт упёр движение SMC (=фактически аппаратно) — дескриптор не завершается → XDMA h2c FSM BUSY.
2. **Фактор невосстановимости (confirmed):** драйвер не имеет программного reset канала (bit31 / SGDMA_COMMON.control), поэтому после триггера движок нельзя вернуть в idle из host.

> *2-я часть — достоверность «высокая» на уровне кода (нет reset путей — факт). Механизм «застрявший write в SMC/MIG» — высоковероятный спусковой (соответствует всем наблюдениям F1–F5), но для стопроцентного подтверждения нужен сигнал-лог (прogrип SMC/MIG или захват AXI) — за пределами этого read-only аудита.*

## 6. Разделение «подтверждено» vs «предположение»

**Подтверждено кодовым аудитом (факт):**
- Банк дескрипторов 2049, для 500 КБ клэмп не срабатывает (H1).
- 500 КБ → один WDF-пакет, multi-packet путь не задействован (H2).
- Драйвер НЕ использует `XDMA_CTRL_RST` и НЕ пишет `SGDMA_COMMON.control`; все «сбросы» = RUN=0 (H3/H4).
- RTL-сторожевые/abort управляют ядром tdot, а не XDMA h2c (H6).

**Предположение (высокая гипотеза, требует железного подтверждения):**
- Зависший posted-write в SMC/MIG — точный аппаратный триггер. Не подтверждается из кода однозначно без захвата AXI на плате.

## 7. Рекомендации (для будущего, вне рамок этого read-only аудита)

1. **Программный reset канала** — добавить прописывание `XDMA_CTRL_RST (bit31)` в `controlW1S` затем обратную рассинхронизацию, и `SGDMA_COMMON.control` global reset (по PG195: reset ставит движок в idle, сбрасывает дескрипторы) — позволит host-глушить аппаратный BUSY без reboot.
2. **Ограничить размер одиночного h2c** ≤ на «безопасный» порог (например 4–16 КБ) — обходной путь, избегающий насыщения SMC (аналог исторического 512Б-кэпа, но без потери).
3. **Перенести h2c-данные на отдельный порт / отдельный SMC** или включить MIG `WR`-приоритет для точки входа, чтобы длинные записи не голодали при RD_PRI_REG.
4. **Датчик busy/hang** — в `EvtDmaWatchdogTimer`/WaitCompletion при N подряд timeout переходить к программному reset (п.1).
