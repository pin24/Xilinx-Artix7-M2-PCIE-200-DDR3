## 1. Главный вывод: «сломалось после обновлений» — это не регрессия кода

Три независимых факта:

1. **Прошивка в интервале не собиралась и не шилась.** `docs/CHANGE_LOG_2026-10-22.md:74`,
   и `git log --name-only 496272b..HEAD -- *.bit *.bin *.dcp *.ltx` — пусто.
   Значит вся RTL-работа этой сессии (watchdog'и AXI, controller-abort, регистры
   0x62/0x63, ширина `dp_wdog_cnt`, `GLOBAL_RETIMING`) **физически отсутствует на
   плате**. Наблюдаемое поведение железа ею объясняться не может.
2. **Wedge большого h2c существовал и раньше**, но был невидим: до 1.2.7.4 IRP на
   таймауте не завершался вообще (висело навсегда, без ошибки). 1.2.7.4 корректно
   завершает его `STATUS_IO_TIMEOUT` → в логе появляется `timeout at 0x200000`.
   То есть обновление **проявило** дефект, а не создало.
3. **Восстановления нет по причине в железе**: BIT31 канального `control`
   (Reserved в XDMA IP v4.2) на этом битстриме — no-op (BUG-081, проверено на
   железе: reset вернул 0, 64 Б после него снова timeout). WHEA/0x124 = 0 за 6 ч
   → тихий stall, не ROF.

Вердикт: **ранее скрытый аппаратный предел** (posted-write большого h2c застревает
на пути `xdma_axi_smc → MIG` при `nextAdj=0`, движок остаётся BUSY, self-timeout у
него нет). Уверенность: высокая по «не регрессия», средняя по точному
микро-механизму (нужен AXI-захват при живом железе).

## 2. Что реально дефектно в коде (проверено построчно)

### D1 — HIGH: двойное завершение IRP на гонке «cancel ∩ timeout» (риск BSOD 0x10D/UAF)
`sys/file_io.c:1095-1119`. Гард написан наоборот для целевого сценария:

```c
pollTimeout = engine->txnTimeout;                 // :1098
NTSTATUS st = WdfRequestUnmarkCancelable(request); // :1101
if (st == STATUS_CANCELLED && !ownTxn && !pollTimeout) return;  // :1102
```

Если bounded-полл уже истёк (`dma_engine.c:1728` ставит `txnTimeout = TRUE` и
захватывает `txnDone`), а cancel-рутина в этот момент получает
`STATUS_CANCELLED`, то `pollTimeout == TRUE` → раннего выхода **нет** → cancel
делает `EngineStop` + `WdfDmaTransactionRelease` + `WdfRequestComplete`
(`:1106-1119`), хотя полл уже объявил себя владельцем и вызывающий
`EvtIoWriteDma` завершит request сам (в его хвосте `owner == FALSE` —
«already claimed, completing to avoid wedge», `:864-869`). Итог — два
`Release`/`Complete` на одном объекте.
Фикс: финализировать **только по `ownTxn`**; при `st == STATUS_CANCELLED`
выходить без `!ownTxn && !pollTimeout`. Комментарии в `dma_engine.h` и
`dma_engine.c:1728` («poll-owner will NOT complete») противоречат хвосту
`file_io.c`.

### D2 — CRITICAL (латентно): DP-watchdog по-прежнему мёртв
`rtl/integration/tdot_axi4.sv:810-811,955`:
`localparam DP_WDOG_MAX = (1 << 22)` (= 4194304) при `logic [21:0] dp_wdog_cnt`
(максимум 4194303), сравнение `dp_wdog_cnt >= DP_WDOG_MAX` → **никогда не
истинно**. BUG-078 закрыт преждевременно: нужен бит 22, т.е. `[22:0]`.
Подтверждено отдельным xsim (25,165,824 тактов без прогресса — `fired` не поднялся).

### D3 — HIGH: controller-abort дропает completion молча
`tdot_axi4.sv:984-994`: по `rd_to_fire || wr_to_fire` задача ретирится
(`busy_q <= 0`, `sched_rptr_q + 1`, `done_cnt_q + 1`, `cstate <= CS_IDLE`), но
слот в `COMP_BASE` (`:1205-1218`, `CS_CMP1..CS_CMP3`) **не пишется**. Хост
`collect()` читает по `done_cnt` старый слот → **устаревший result/status
выдаётся как валидный**. Нужно писать W0/W1 со status=timeout либо запретить
чтение по event-битам 0xF8/0xFC.

### D4 — HIGH: abort не очищает DP-FSM
Тот же блок не сбрасывает `use_dp_q`/`dprog_active_q`, не пишет mailbox и не
дренирует FIFO-задачи → в связке с D2 программный режим зависает до нового batch.

### D5 — MED: `ValidateBarParams` off-by-one
`sys/file_io.c:296-301`: `if (offset + length >= xdma->barLength[nBar])` —
доступ к последнему слову/байту BAR отклоняется (должно быть `>`). Достижимо на
граничных чтениях регистров.

### D6 — MED: `actual >= expected` по накопительному `completedDescCount`
`dma_engine.c:558` и `:1685`. Счётчик IP нигде программно не обнуляется, поэтому
на multi-packet переносе возможен ложный «успех» (перенос объявлен готовым до
завершения). Нужно сравнение по дельте `(actual - snapshot) & mask >= expected`
со снапшотом под `engineLock`.

### D7 — MED: кольцо 256 (хост) vs 1024 (RTL)
`pytorch_layer/xdma_driver.py:923` — `SCHED_RING_DEPTH = 256`, маска `0xFF`;
RTL — mod-1024 (`tdot_axi4.sv:263-264`), `rmask`/occupancy в `obs_smi` считаются
по 0x3FF. На текущей (старой) прошивке это совпадает с железом, но после прошивки
RING-1024 хост надо переводить на `ring_depth=1024`, иначе doorbell упирается в
8/10-битную границу.

### D8 — LOW: `OBS_REGMAP_V = 1` не отражает 0xF4/0xF8/0xFC
`obs_smi.py` на старой прошивке покажет ложно-чистый «rd=0 wr=0» вместо «n/a» —
нужен ревизионный бамп.

### D9 — LOW: `rd_timeout_sticky`/`wr_timeout_sticky` — dead-сигналы
Устанавливаются, нигде не читаются и не сбрасываются, кроме reset.

## 3. Что проверено и признано исправным

- **Регистры ядра 0x00…0xE0**: `ADDRESS_MAP.md` ↔ декодер `case addr[7:2]` ↔
  `xdma_driver.py`/`obs_smi.py` — совпадение индекс-в-индекс; ловушка
  word-vs-byte (0x62/0x63 vs 0xF8/0xFC) никем в коде не нарушена.
- **Адресация**: база DDR3 `0x8000_0000` добавляется один раз, LO/HI 64-бит,
  выравнивание ≥4 / 4 КБ для SG, окно AXI-Lite 128 МБ (`0x4000_0000..0x47FF_FFFF`),
  BAR0 = 128 МБ AXI-Lite, BAR2 = MSI-X, 2+2 канала, XDMA IP **v4.2**
  (`xdma_ddr3_dfx_bd.tcl:662`), KMDF 1.11 — расхождений нет.
- **Протоколы**: формат SGDMA-дескриптора и completion/tag согласованы с
  драйвером; `nextAdj = 0` — осознанная анти-ROF мера; банк 2049 дескрипторов и
  `XDMA_MAX_TRANSFER_SIZE` согласованы с `DMA_CHUNK`.
- **RTL-таймауты read/write**: ширина (`1<<19` в 20 бит) корректна, счётчики
  обнуляются в ветке срабатывания (`:658`, `:745`), ложных срабатываний на
  легальном burst нет, мульти-драйва NBA на `r_ready_r`/`ar_valid_r`/`aw_valid_r`/
  `w_valid_r` нет.
- **Эмуляция**: `verify_tdot_axi4.py 32` → 4/4, несовпадений 0;
  `tb_timeout_abort` → PASS (watchdog, `busy=0`, повторный таймаут).
- **Боевые пути**: штатный успех и одиночный таймаут завершаются ровно один раз;
  пути `STATUS_CANCELLED` и `packet >= XDMA_MAX_WDF_PACKETS` корректны;
  IOCTL 0x7 (METHOD_BUFFERED) безопасен и обратно совместим.

## 4. Приоритет действий

1. **D1** — единственный дефект с риском BSOD; правится в драйвере без железа,
   проверяется под Driver Verifier.
2. **D2/D3/D4** — правки RTL, накапливать к следующей сборке; **D3 обязателен до
   прошивки**, иначе abort превратит зависание в тихую порчу данных.
3. **D5/D6/D7/D8/D9** — мелкие, каждый в одну строку/константу.
4. **Превентивная митигация wedge** (без записи в плату): ограничить размер
   одиночного h2c (≤ 4–16 КБ, дробление в `write_dma`/кольце) — единственная
   реальная защита, пока `BIT31`-reset не работает.
5. После разрешения записи: sweep размера h2c на чистом движке → порог; A/B
   `completedDescCount` между переносами (D6); `bit31`+`GLOBAL_RETIMING` — только
   на **новом** битстриме.

## 5. Ограничения

- Плата в состоянии wedged; таймауты чтения не трактовались как находки.
- Механизм `xdma_axi_smc → MIG` (write-priority `RD_PRI_REG`) и полный CDC-профиль
  125↔MIG требуют живого железа и AXI-захвата.
- D1 подтверждён чтением кода и моделью владения, но не воспроизведён под
  Driver Verifier (требует гонки).
- D2 подтверждён xsim-прогоном в этой сессии; D3/D4 — только чтением кода.
