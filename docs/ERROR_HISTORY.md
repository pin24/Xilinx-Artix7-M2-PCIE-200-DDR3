## 2026-09-06 — Сборка NUM_MAC=8: CARRY4 overflow, Place 30-487 (20346 слайсов)

### [BUG-037] NUM_MAC=8 превышает слайсы по CARRY4 — 16241 блоков, 20346 слайсов требуется

| Поле | Значение |
|------|----------|
| **Где** | `rtl/block/tfmul_raw.sv` (40-тритная carry-save редукция, 5 уровней CARRY4), `scripts/build_dfx.tcl` |
| **Симптом** | `make build NUM_MAC=8 JOBS=10` — синтез 0 ошибок, но `place_design` падает: `ERROR: [Place 30-487] There are a total of 26550 slices in the device, of which 10281 slices are available, however, the unplaced instances require 20346 slices.` |
| **Ресурсы (синтез)** | LUT: 106 985 (79,5%), CARRY4: 16 241 (48,3%), BUFG: 1. LUT-утилизация приемлема, но CARRY4-плотность не позволяет упаковать логику: каждый CARRY4 занимает отдельный слайс, и они не могут быть спаркованы с другой логикой в том же слайсе. 16 241 CARRY4 + остальная логика = 20 346 слайсов, доступно 10 281 (остальные заняты BRAM/DSP/IOB). |
| **Причина** | `tfmul_raw` содержит ~2000 CARRY4 на экземпляр (40-тритная balanced-редукция × 5 итераций carry-save). 8 экземпляров = 16 241 CARRY4. Пайплайн внутри `tfmul_raw` (25 тактов на умножение) использует один и тот же комбинаторный конус на каждом такте — CARRY4 не расшариваются между тактами. |
| **Сравнение** | NUM_MAC=16: 123k LUT, ~18,5k CARRY4, WNS=-120ns (тайминг-фейл); NUM_MAC=8: 107k LUT, 16,2k CARRY4, Place 30-487; NUM_MAC=4: ~55k LUT, ~8k CARRY4 — ожидается влезание. |
| **Попытки исправления** | (1) `tfmul_kbd` (Karatsuba 10×10, комбинаторный) — 316K LUT (235%). (2) `tfmul_kbd` последовательный (3×trit_mul10x10 за 21 такт + 41 такт финал) — 175K LUT (130%), CARRY4 103% — не влезло. (3) Оба варианта kbd отвергнуты — возврат к `tfmul_raw`. |
| **Направление исправления** | (1) Пайплайнизация `tfmul_raw`: разбить 40-тритную carry-save цепочку на 2-3 стадии с регистрами между ними — уменьшит CARRY4-уровни с 263 до ~80-130, что позволит place'ру эффективнее упаковать логику. (2) Либо временно NUM_MAC=4 для работающей сборки. |
| **Статус** | 🔴 **Критический** — сборка NUM_MAC=8 не проходит place. Требуется пайплайнизация tfmul_raw или уменьшение NUM_MAC. |

## 2026-09-06 — Шаг 2 дерева (ADDERS barrel-аддеров) + BUG-041: нулевые операнды tfadd_raw

### [BUG-041] tfadd_raw: нулевой операнд с «большой» экспонентой уничтожал ненулевой (x+0 == 0)

| Поле | Значение |
|------|----------|
| **Где** | `rtl/block/tfadd_raw.sv` (PH_IDLE: выбор big/small по ЭКСПОНЕНТЕ без анализа нулевых мантисс); тот же дефект в замороженной `tfadd_raw_ref.sv` и в golden `_raw_add` (verify_compute_dot_par_raw.py — там, наоборот, zero-shortcut БЕЗ нормализации) |
| **Симптом** | ЛАТЕНТНЫЙ, железом не диагностировался: wall-векторы (uniform floats) никогда не дают нулевых мантисс. Реальный кейс — тернарные веса {-1,0,+1}: нулевой TFloat48 = (m=0, e=0) → продукт (0, e_data−18) с мусорной экспонентой до +22; нулевая частичная сумма дерева = 48'h0 (e=0). Если нулевой операнд оказывался «большим» по e, ненулевой уходил в m_small и сдвигался на min(\|Δe\|,22) тритов: при \|Δe\|>22 — ТЕРЯЛСЯ ПОЛНОСТЬЮ (x+0 == 0), при \|Δe\|≤22 — огрызался. Поражает уровень 0 дерева И все уровни ≥1, а также long-dot (tfadd48→tfadd_raw) |
| **Причина** | Экспонента нулевого операнда не имеет смысла, а аддер доверял ей как шкале; golden-модель отличалась от RTL (shortcut без нормализации vs отсутствие shortcut) — расхождение не проявлялось на ненулевых векторах |
| **Исправление** | (1) tfadd_raw: za/zb — 80-битное детектирование нулевых мантисс в PH_IDLE; нулевой операнд выбрасывается, ненулевой идёт как big с k=0: x+0 == norm(x), 0+0 == 0. (2) golden `_raw_add`: zero-shortcut теперь нормализует (`_norm_raw_rtl`), т.к. выход tfadd_raw ФИЗИЧЕСКИ всегда нормализованный TFloat48 — «отложить нормализацию» интерфейс не может; иначе другой порядок округления на уровнях дерева (расхождения в младших тритах на векторах с нулями) |
| **Проверка** | `rtl/block/proof_tree_par.py` Z1: 20120 векторов (x+0==norm(x), 0+0==0; старая семантика расходится в 6099/20120 — баг продемонстрирован количественно); Z2: 5000 векторов (ненулевые не затронуты); T1: 180 деревьев с нулями/тернарными весами == golden бит-в-бит. Стена: tb_tfadd_equiv дополнен зоной Z41 (направленные + 300 случайных с нулём; расхождение new-vs-ref в зоне ОЖИДАЕМО, Z41_DIFF>0 обязателен); verify_compute_dot_par_raw.py генерирует тернарные/нулевые профили |
| **Статус** | ✅ Исправлен (вместе с Шагом 2). tfadd_raw_ref.sv — предупреждение в шапке (зона BUG-041, логика заморожена) |

### Попутно: транскрипционная ошибка exp_code в proof-модели Шага 1 (НЕ RTL)

| Поле | Значение |
|------|----------|
| **Где** | `rtl/block/proof_tfadd_barrel.py` (exp_code: `rv == -2 → code = 2`) — Python-модель; в SV-RTL `tfadd_raw.sv`/`tfadd_raw_ref.sv` КОД ВЕРЕН (`rv == -2 → 2'b01` = P1) |
| **Симптом** | Модель кодировала отрицательные экспоненты e ≡ 1 (mod 3) со сдвигом: e=−2 → код (N1,N1) = −4, e=−11 → −13 (коллизии!). Найдена proof_tree_par.py T1 (модель-vs-golden расхождение в экспоненте) и локализована поузловой трассой; T0 дополнен оракулом «dec(enc(e)) == e», который ловит самосогласованные кривые кодировщики |
| **Влияние** | На выводы A0–A6 НЕ влияло (обе стороны сравнения использовали один и тот же exp_code — self-consistency); влияние — только на абсолютную кодировку pack48 в модели. RTL-железо не затронуто |
| **Исправление** | `rv == -2 → code = 1` в proof_tfadd_barrel.py и копии в proof_tree_par.py; регрессия: proof_tfadd_barrel.py — ALL PROOFS PASSED после фикса |
| **Статус** | ✅ Исправлено в обеих Python-моделях |

**Урок** (BUG-041): «нуль» в позиционном формате с экспонентой — не нейтральный элемент для АЛГОРИТМА выравнивания: мусорная шкала нулевого операнда убивает ненулевой слагаемый. Детект нулей обязателен на входе сумматора, если нули возможны в потоке (тернарные веса!). Урок (модель): энкодер проверяется оракулом «enc→dec == identity», а не парой «мой энкодер + мой декодер» — самосогласованная пара скрывает любые систематические сдвиги.

## 2026-09-06 — Баррелизация tfadd_raw (Шаг 1 дерева): латентный баг обрезки |Δe| по mod 64

### [BUG-040] tfadd_raw: cnt[5:0] обрезал |Δe| по mod 64 — при |Δe| ≥ 64 выравнивание шло по мусорному сдвигу

| Поле | Значение |
|------|----------|
| **Где** | `rtl/block/tfadd_raw.sv` (PH_IDLE: `cnt <= a_e - b_e` в 6-битный cnt; PH_INIT: кламп ≤22) |
| **Симптом** | ЛАТЕНТНЫЙ, в железе не диагностировался. tfmul_raw выдаёт e_prod = ea+eb−18 ∈ [−98, 62] (экспоненты операндов до ±40) → разброс |Δe| между двумя продуктами одной точки достигает **160**, а 6-битный cnt арифметически обрезает по mod 64: Δe=64 → cnt=0 (малый продукт добавлялся в масштабе большого, ошибка до ×3^64), Δe=65 → cnt=1, Δe=128 → 8-битное переполнение самой разности. Достижимо на уровнях дерева ≥1 и в long-dot (tfadd48→tfadd_raw, e ∈ [−40,40], Δe до 80 → 80 mod 64 = 16) |
| **Причина** | Разность экспонент писалась в 6-битный регистр без проверки диапазона; кламп «>22» применялся уже к обрезанному значению |
| **Исправление** | В barrel-версии tfadd_raw (Шаг 1 пайплайнинга дерева, разрешено пользователем): разность Δe считается в 9 битах, k = min(\|Δe\|, 22) — проектное намерение serial без бага. Фикс получен автоматически, без изменения семантики в валидной зоне |
| **Проверка** | `rtl/block/proof_tfadd_barrel.py` — ALL PROOFS PASSED, 282k+ векторов: (A5) полный конвейер serial==barrel бит-в-бит при \|Δe\|≤63 (110 300 векторов); (A6) barrel==intent на всём Δe 0..160 (30 000 векторов), serial с багом расходится в 2880/30000 случаев Δe≥64. A/B на xsim за стендом: `tb_tfadd_equiv.sv` (new vs golden-копия `tfadd_raw_ref.sv`, pass/fail + латентность==6 тактов) |
| **Статус** | ✅ Исправлен в barrel-версии (вместе с Шагом 1). Golden-копия `tfadd_raw_ref.sv` оставляет серийное поведение как эталон — валиден при \|Δe\| ≤ 63 (предупреждение в шапке) |

**Урок** (BUG-040): ширина счётчика выравнивания = ширина РАЗНОСТИ экспонент входов, а не «сколько итераций делаем» — кламп применяется к полной разности, не к обрезанной. Диапазоны экспонент выходов модулей-поставщиков (tfmul_raw: e ∈ [−98, 62] при 8-битных e операндов) фиксировать в шапках модулей и проверять при стыковке.

## 2026-09-06 — ВЕРДИКТ: tfmul_kbd — тупик для данного чипа; в сборке остаётся tfmul_raw

### [DECISION-001] Параллельный Karatsuba-умножитель tfmul_kbd НЕ даёт сокращения элементов — подключение отменено

| Поле | Значение |
|------|----------|
| **Где** | `rtl/block/tfmul_kbd.sv` (остаётся в репо как эталон), `rtl/block/tfmul_raw.sv` (остаётся в сборке: `compute_dot_par_raw.sv:31`, `build_dfx.tcl:314`) |
| **Решение** | **tfmul_kbd признан ТУПИКОМ для xc7a200t**: параллельный Karatsuba НЕ даёт сокращения оборудования относительно последовательного tfmul_raw. Переключение MUL_IMPL (в любом виде) ОТМЕНЕНО; пайплайнизация kbd (16–20 стадий, обещание из BUG-037) — отменена как нецелесообразная. Модуль остаётся в репозитории: (1) точный эталон для тестов после BUG-039, (2) резерв на случай будущих DSP-/carry-lookahead-вариантов |
| **Основание 1: LUT** | Исходная оценка «экономия ~69% LUT (55k→17k)» — ОШИБОЧНА, удалена из заголовка модуля (63795ee). Реальная стоимость: mul_10x10 = 100 PP-тритов (~100 LUT) + 20 колонок × 10-входовые троичные суммы (~35–50 LUT/колонку) ≈ **~1000 LUT/умножитель**; Karatsuba = 3 шт/lane ≈ 3k LUT, flat 4×10×10 ≈ 4k. Последовательный tfmul_raw: 1 общий tbyte_mul (~300 LUT) + 40 колонок × 3-входовые суммы (~12 LUT) ≈ **0.9–1.5k LUT/lane**. Итого parallel-вариант в **2–3 раза ДОРОЖЕ** по LUT на всю иерархию (×NUM_MAC) |
| **Основание 2: латентность** | Серийные balanced-цепочки (div3-перенос колонка→колонка) без тернарного carry-lookahead дают ~35–50 стадий — НЕ лучше raw (~49 тактов после 7da39e5); carry-save сходится 1 колонка/такт (~45 тактов). Тернарный carry-lookahead (кусочно-постоянные функции переноса) — высокий риск, локально неверифицируем (verilator/iverilog в контейнере нет) |
| **Основание 3: система** | Латентность dot-операции доминирует дерево tfadd_raw: NUM_MAC=32 → 31 ПОСЛЕДОВАТЕЛЬНОЕ сложение × ~30–50 тактов (ALGN ≤22 + NORM-циклы, data-dependent) ≈ 1000–1500+ тактов. Умножитель = ~3–5% латентности точки — его ускорение не даёт значимого выигрыша |
| **Проверка** | Анализ Task 17 (worklog): перечитаны tfmul_raw/tfadd_raw/compute_dot_par_raw; цифры сведены в заголовке tfmul_kbd.sv (коммит 63795ee). BUG-039-версия kbd верифицирована (0 ошибок, 100k векторов) — эталонная ценность сохранена |
| **Статус** | ✅ Закрыто решением. Следующая реальная цель оптимизации латентности точки — **пайплайнинг дерева tfadd_raw** (потенциал ~10×), а не умножитель |

**Урок** (DECISION-001): параллелизм колонок в троичной арифметике — НЕ синоним экономии: последовательная схема с одним общим подмножителем (tbyte_mul) дешевле N параллельных колонок с 10-входовыми суммами, а латентность точки определяет дерево СЛОЖЕНИЙ, а не умножитель. Оценки «экономии X%» проверять поколоночной стоимостью ДО проектирования RTL.

## 2026-09-06 — Точность tfmul_kbd: 43.9% неверных произведений (Karatsuba-усечение + carry_val)

### [BUG-039] tfmul_kbd: средний член Karatsuba усечён до 10 тритов + carry_val в mul_10x10 обрезан до 2 бит

| Поле | Значение |
|------|----------|
| **Где** | `rtl/block/tfmul_kbd.sv` (function mul_10x10; always_comb — средний член Karatsuba) |
| **Симптом** | Файл НЕ подключён к сборке (см. BUG-037), поэтому в железе не проявлялся. Модельный прогон построчной Python-модели RTL: **43.9% случайных пар мантисс дают НЕВЕРНЫЙ продукт**, абсолютная ошибка до ~3^30 (младшие ~30 тритов из 41 — мусор); крайний случай a=b=все «+1» тоже неверен |
| **Причина 1** | Средний член Karatsuba — умножение СУММ половин (A_hi+A_lo)(B_hi+B_lo). Полные суммы занимают HALF+1=11 тритов (29524+29524=59048 > (3^10−1)/2), код усекал их до младших 10 тритов (`a_sum_short = a_sum_local[2*HALF-1:0]`) — перенос s ∈ {−1,0,+1} в 11-й трит выбрасывался. Терялись члены (s_a·b_mod + s_b·a_mod)·3^10 + s_a·s_b·3^20 среднего произведения → ошибка до ~3^30 в итоговом продукте |
| **Причина 2** | `carry_val` в mul_10x10 объявлен `logic signed [1:0]` (−2..1), но q = col_sum/3 достигает ±5 (до 10 частичных произведений в колонке + перенос): присвоение `carry_val = q[1:0]` обрезало — например +2 хранилось как −2 → неверные произведения уже внутри подмножителей |
| **Связь с BUG-037** | Уточнение атрибуции: регистры критического пути b_mr_reg/prod_r_reg принадлежат **tfmul_raw** (a_mr/b_mr/prod_r); у tfmul_kbd регистры prod_q/e_q/neg_q. Фикс 7da39e5 корректно исправил tfmul_raw (carry-save pipeline). BUG-037 в заголовке назвал tfmul_kbd — фактически собран был tfmul_raw |
| **Исправление** | s-коррекция (эквивалент mul_11x11 БЕЗ роста дерева): перенос s УЖЕ вычислялся в a_sum_local/b_sum_local[2*HALF +: 2] и выбрасывался — теперь используется: `mid = a_mod*b_mod + 3^10*(s_a*b_mod + s_b*a_mod) + 3^20*(s_a*s_b)`, где s·x для одиночного трита — знаковый мультиплексор (±x/0), без дерева частичных произведений. corr1 = s_a*b_mod + s_b*a_mod (11 тритов, колонковое сложение), слияние в mul_sum_mid (21 трит: |A_sum·B_sum| ≤ (3^10−1)^2 < 3^21/2). carry_val расширен до `logic signed [3:0]`, присвоение `q[3:0]`. Ширины колонок: tot1/tot2 ≤ ±6 → [3:0] |
| **Проверка** | (1) Построчная Python-модель RTL `ternary_sw/model_tfmul_kbd.py`: **0 ошибок** на 72 направленных кейсах (все 16 комбинаций крайних половин → s_a,s_b ∈ {−1,0,+1}, s_a·s_b = ±1, нули, ±1, max·min, разные экспоненты) + 100 000 случайных векторов (проверка prod/e/neg против прямого целочисленного умножения); контроль фиделити — старая версия на тех же векторах неверна на 44.0%. (2) `ternary_sw/ternary_kbd_ref.py` (эталон, не менялся): 100/100. (3) `rtl/block/tb_tfmul_kbd.sv` — self-checking тестбенч (golden = longint-умножение + преобразование в 40 тритов): 3026 векторов, запуск за стендом (xsim: `xvlog tfmul_kbd.sv tb_tfmul_kbd.sv && xsim tb_tfmul_kbd -R`). (4) `scripts/sv_lint.py` (баланс конструкций): tfmul_kbd.sv/tb_tfmul_kbd.sv OK |
| **Статус** | ✅ Точность исправлена (модельный уровень). ⚠️→✅ В сборку НЕ подключён и ПОДКЛЮЧЕН НЕ БУДЕТ — см. DECISION-001 (тупик: 2–3× LUT-дороже raw, латентность не лучше; пайплайн 16–20 стадий отменён как нецелесообразный). Остаётся эталоном/резервом |

**Урок** (BUG-039): Karatsuba-разбиение ВСЕГДА даёт (n+1)-тритные суммы половин — усечение среднего члена до n тритов портит почти половину результатов, это не угловой кейс. Переносы, уже вычисленные в промежуточных шинах, не выбрасывать: s-коррекция даёт точность mul_11x11 бесплатно (пара знаковых мультиплексоров вместо дерева). Ширины переносов считать от максимума колонки (частичные произведения + накопленный перенос), а не «на глаз». Новые RTL-модули верифицировать построчной Python-моделью против прямого умножения ДО синтеза — tb и модель ложатся в репозиторий рядом с эталоном.

## 2026-09-07 — Pure-LUT tfmul_raw/tbyte_mul: устранение источника 16241 CARRY4 (BUG-037 CARRY4, продолжение)

| Поле | Значение |
