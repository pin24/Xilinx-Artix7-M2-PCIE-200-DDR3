## 1. Расхождения карты регистров

Сверены: ADDRESS_MAP.md §3 ↔ xdma_driver.py (модульные константы + `TdotCore`/`TdotScheduler`)
↔ tdot_axi4.sv (декод `[7:2]`). RTL удекаживает байтовый offset = поле×4. Совпадение по
всем рабочим регистрам (CTRL 0x00…DONE_CNT 0x60, CORE_RES 0x2C/0x30, планировщик 0x40–0x60,
OBS 0x6C–0xE0, дескриптор W3 n_total[31:16]/tag[15:0] — пакование в `submit()` совпадает с RTL
`desc_w[3][31:16]/[15:0]`). **ЕДИНСТВЕННОЕ** расхождение:

| Регистр | ADDRESS_MAP | xdma_driver.py | RTL | Вывод |
|---|---|---|---|---|
| CAPS `0x74`, бит `[16]` "sched" | `[16]` = sched (наличие планировщика) | `read_caps()['sched'] = bool((v>>16)&1)` (xdma_driver.py:684) | бит16 захардкожен `1'b1` (tdot_axi4.sv:406) | **Расхождение ADDRESS_MAP↔RTL**: RTL всегда выдаёт `sched=True`, признак реального наличия планировщика из железа не читается. Драйвер следует ADDRESS_MAP, что привело бы к ложному «sched включён» при чтении CAPS. |

Это диагностические данные (`read_caps` не влияет на основной путь dot), поэтому severity P3.

Прочие несовпадения не подтверждены: базы периферии (GPIO/DFX/TDOT/ICAP/SPI/XADC), окна
AXI (0x40000000 AXI-Lite, 0x80000000 DDR3), DMA-смещения как есть (без добавления DDR3_BASE)
— согласованы во всех трёх источниках.

## 2. Находки по severity

### P1 (неверный результат / падение / порча данных)

Нет подтверждённых P1: обработка CreateFileW-ошибок корректна (`not h or h == INVALID`,
ctypes возвращает None для NULL-return), адресная арифметика 32/48 бит согласована с RTL.

### P2 (латентные дефекты, ресурсы, потокобезопасность)

1. **P2, xdma_driver.py:259-265 (XdmaWinDriver)** — утечка дескрипторов: `self._h` (=CreateFileW)
   нигде не закрывается; при сбое CreateEventW (стр. 264) открытый `_h` теряется. Нет `close()`,
   `__del__`, `__exit__` ни в одном ctypes-бэкенде. Сценарий: многократное создание
   `XdmaWinDriver()` без явного close течёт хэндлы/Event до исчерпания дескрипторов процесса.
   Рекомендация: управляемый контекст (context manager), закрывать `_h` и `_ev` в `__del__` and
   в ошибках инициализации.

2. **P2, xdma_driver.py:471-499 (XdmaWinUpstream._xfer)** — один общий событийный хэндл `_ev`
   и регистр-баффер на все каналы/обращения; метод не потокобезопасен. `ResetEvent` перед каждой
   операцией при конкурентных `read`/`_h2c`/`_c2h` с одного инстанса даёт гонку на `ov.hEvent`
   (одна операция сбросит событие другой). Рекомендация: отдельные `_OVERLAPPED.hEvent` на
   вызов, либо сериализация экземпляра локом.

3. **P2, xdma_driver.py:455-459, 462 (XdmaWinUpstream.__init__)** — частичная инициализация
   теряет уже открытые хэндлы: если `_ctl`/`_usr` открыты, а затем падает `_open(h2c_0)` (стр.465),
   `_ctl` и `_usr` не закрываются. Также `_ctl`/`_usr` открываются по принципу «все-или-ничего»
   глотав ошибки (см. обращение с OSError ниже). Рекомендация: try/finally-закрытие всех уже
   открытых хэндлов при сбое инициализации.

4. **P2, xdma_driver.py:416-417, 446-449 (XdmaWindows.write_dma / _run_channel)** — DMA-запись
   выполняется ОДНИМ вызовом xdma_rw.exe через временный файл БЕЗ разбиения на чанки, в отличие
   от XdmaLinux/XdmaWinUpstream (`DMA_CHUNK=1MiB`). Для больших буферов (например длина >1 МиБ,
   или близкая к 2 ГБ) xdma_rw/файл/`-l` может упереться в ограничения инструмента/файловой
   системы. Рекомендация: чанковать по DMA_CHUNK как в остальных бэкендах.

5. **P2, xdma_driver.py:914-915 (TdotScheduler.submit)** — `_wptr` и указатели кольца — состояние
   экземпляра без лока; два потока на одном `TdotScheduler`/`dev` гонят `_wptr`, doorbell и DMA
   дескрипторов. Требование «не подавать новый батч до wait()» (строки 866-867) не защищено кодом.
   Рекомендация: задокументировать явно однопоточность либо добавить лок.

6. **P2, xdma_driver.py:692 (obs_clear) / 696 (obs_freeze)** — RTL (tdot_axi4.sv:328-330) при
   ЛЮБОЙ записи в OBS_CTRL ставит `obs_freeze_q <= wdata_q[1]` и `obs_clear_q <= wdata_q[0]`.
   `_reg_w(OBS_CTRL, 0x1)` из `obs_clear()` сбросит текущий FREEZE (чужой бит), а
   `_reg_w(OBS_CTRL, 0x2)` из `obs_freeze(on)` выставит clear=0 (безопасно, но не read-modify-write).
   Сценарий: `obs_freeze(True)` затем `obs_clear()` — freeze незаметно выключится. Рекомендация:
   перед записью читать предыдущее значение и сохранять нецелевой бит (read-modify-write).

### P3 (полнота/гигиена, диагностика)

7. **P3, xdma_driver.py:943-944 (TdotScheduler.wait)** — `except OSError: pass` глотает все
   ошибки чтения `/dev/xdma0_events_0`, включая реальные I/O-ошибки, и молча переключается на
   поллинг. Рекомендация: лог-сообщение вместо тихого pass.

8. **P3, xdma_driver.py:1030 (селект** – `except (XdmaError, NameError)` в `_selftest` ловит
   `NameError` слишком широко — может замаскировать реальную ошибку имени при импорте/исполнении,
   а не отсутствие устройства. Рекомендация: только `XdmaError`.

9. **P3, xdma_driver.py:108 (OBS_CTRL адреса в комментарии)** — нет, фактически: смещение 0x6C —
   комментарий на строке 348 «0x6C=6'd27» согласован. Не находка.

10. **P3, xdma_driver.py:997 `_pack_tf48` (модульная) vs :748 `pack_tf48` (метод TdotCore)** —
    дублирование почти идентичной логики; `pack_tf48` (метод) дополнительно режет до 6 байт.
    Рекомендация: один helper.

11. **P3, магические константы дублированы в нескольких местах** (см. §3).

12. **P3, xdma_driver.py:748-764 (packed-путь i*6)** — `write_tf48_packed/read_tf48_packed/`
    `pack_tf48` используют 6-байтный шаг, но RTL (tdot_axi4.sv) читает i*8 (64-битное слово, §6).
    Формат несовместим с текущим RTL (в комментарии 743-747 это признано «отдельной RTL-задачей»).
    API является западнёй: вызов даст неверные данные без явной ошибки. Рекомендация: убрать или
    явно пометить `NotImplementedError`.

13. **P3, отсутствие закрытия хэндлов при выдёргивании платы** — ни один ctypes-бэкенд не проверяет
    удаление устройства: чтение по устаревшему хэндлу вернёт WinError, но хэндлы/событие не будут
    освобождены и переоткрыты; сообщение об ошибке не отличит «плату вынули» от прочего сбоя.
    Рекомендация: ловить ERROR_DEVICE_REMOVED/ERROR_INVALID_HANDLE и закрывать/освобождать.

## 4. CreateFile / DeviceIoControl / чтение-запись

- `XdmaWinDriver`: CreateFileW(overlapped), проверка `not h or h == INVALID` — корректна
  (ctypes возвращает None на NULL). Таймаут WaitForSingleObject 10 с — фикс. Проверка
  GetOverlappedResult с `bWait=False` в синхронной ветке (:294-295) не проверяется статус — но
  операция уже синхронно завершена, возврат-байт берётся из done; безвредно. Отсутствует
  сверка фактически прочитанных байт с запрошенными (`return buf.raw[:n.value]` — если драйвер
  вернул меньше, чем length, это молча принимается). **P2-кандидат**: в `read()` нет проверки
  `n.value == length`.
- `XdmaWinUpstream`: те же паттерны; `read_config` — прямой доступ к config-BAR, ок.
- `XdmaWindows` (xdma_rw): проверка returncode есть; **отсутствует проверка, что `_run`
  вернул ровно `length` байт** на чтении и что запись фактически записала все байты. R-05.

Буферы: `create_string_buffer(data, len(data))`/`create_string_buffer(length)` — для длин до
`DMA_CHUNK` (1 МиБ) переполнения нет; DWORD-параметр длины (32-бит) позволяет максимум 4 ГБ на
вызов — чанкинг это обходит.

## 5. Отображение BAR

Нет прямого MMAP (ctypes-бэкенды идут через драйверные узлы/`xdma_rw`; Linux — открытие
`/dev/xdma*`). BAR-логика сконцентрирована в драйвере: `XdmaWinDriver`/`XdmaWindows` шлют полный
AXI-адрес, `XdmaWinUpstream` сам вычитает `AXI_LITE_BASE` для `\user`-узла. Двойного
освобождения/невыравненного доступа нет. Работа при отсутствии устройства: Linux — проверка
`os.path.exists` + XdmaError; ctypes — WinError при CreateFileW; xdma_rw — returncode. После
открытия удаление устройства не обрабатывается (см. находку 13).
