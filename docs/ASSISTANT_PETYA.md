# Агент-помощник «Петя» — протокол обращения (локальный OpenAI-сервер)

Дата фиксации: 2026-10-08. Категория: локальный LLM-ассистент (второе мнение, анализ, ревью).
Обязателен для будущих сессий: как вызывать, как правильно слать JSON, как читать ответ с think-модулем.

---

## 1. Доступ (проверено на стенде)

- Сервер: `http://127.0.0.1:8080` (OpenAI-совместимый, llama.cpp-подобный).
- Endpoint: `POST /v1/chat/completions` (и `GET /v1/models`).
- Модель: **`swift-1.5-iq2_xs`** (Qwen-based thinking-модель; `n_ctx=131072`).
- `localhost` НЕ доступен через webfetch (инструмент запрещает loopback) — обращаться **только через shell** (`powershell`/`python`/`curl`).

## 2. Правильный JSON (важно)

Тело запроса:
```json
{
  "model": "swift-1.5-iq2_xs",
  "messages": [{"role": "user", "content": "..."}],
  "stream": false,
  "max_tokens": 70000
}
```
КРИТИЧНО:
- Кодировка тела — **UTF-8** (не ASCII!): если нейруки в botàми записать в ASCII, кириллица превращается в `?` и модель отвечает про «вопросики».
- Заголовок `Content-Type: application/json; charset=utf-8`.

## 3. think-модуль (самое важное)

Модель снабжена «думалкой»: ответ приходит в `choices[0].message` двумя полями:
- `reasoning_content` — внутренний рассудок;
- `content` — итоговый ответ.

ПОВЕДЕНИЕ (проверено эмпирически):
- На малых вопросах быстро «додумывает» и выдаёт `content`.
- На БОЛЬШИХ/открытых вопросах думалка расходует **весь** `max_tokens` → `content=""`, `finish_reason=length`. Это НЕ ошибка сервера.
- **Решение:** давать `max_tokens` с большим запасом (напр. **70000** для развёрнутого вопроса) и явно просить «заверши рассуждения и ОБЯЗАТЕЛЬНО выдай финальный развёрнутый ответ». Тогда `finish_reason=stop`, `content` заполнен.
- **Альтернатива для коротких точечных вопросов:** дробить на подвопросы с детальной командой «дай СРАЗУ ответ, без длинных рассуждений».

## 4. Готовый хелпер

Файл: `tools/petya.py` (в репозитории; временная копия — `C:\Temp\gigatool\petya.py`).
```bash
python tools/petya.py "вопрос"
python tools/petya.py --system "ты FPGA-эксперт" "вопрос"
python tools/petya.py --think "вопрос"          # показать и reasoning_content
python tools/petya.py --file prompt.txt --max 70000   # большой вопрос с запасом
```
Печатает `content` в UTF-8; exit 0 при успехе.

## 5. Сводка рекомендаций Пети по проекту (2026-10-08)

Полный текст: `C:\Temp\gigatool\petya_content.txt` (это не в репо; для перечня P-плана см. ниже).

Краткий диагноз:
- Проект LUT-центричный, DSP48 (740) не используются; сумматоры в LUT -> плотность 65%, маршрут 75-83%.
- Deep-adder (24 такта) решил тайминг, но латентность/throughput плохи; дерево-adder становится bottleneck; compute избыточен против PCIe.
- PCIe Gen2 x4 ~133 М пар/с ~1.07 пары/такт — это системный потолок.

Приоритизированный план Пети (P0..P8):
- P0: профилирование (PCIe/DMA/tree/scheduler/IRQ latency).
- P1: **перенести дерево сложения (adder tree) на DSP48 + redundant base-3 + CSA + нормализация один раз в конце** (не гнать тритовое УМНОЖЕНИЕ в DSP). Ожидание: WNS +0.2..0.4, LUT 40-50%, латентность adder 4-6.
- P2: rebalance 16 MAC / 8-4-2-1 (не гнаться за 32).
- P3: XDMA/AXI: MSI-X, descriptors, burst, batching, register slices.
- P4: P&R/floorplan/XDC/CDC.
- P5: XADC на независимом клоке + thermal.
- P6: fallback 110/100 MHz.
- P7: HLS-прототип аккумулятора (не весь проект).
- P8: ring/systolic DSP-архитектура (для long dot).

Замечание (вывод MultiTool): идея CSA/redundant-base-3 с финальной нормализацией — реалистична и предпочтительнее повторения попытки «засунуть тритовое умножение в DSP48» (та попытка уже дала over-utilization). Числа Пети — оценочные; перед реализацией — P0-профилинг + прототип одного DSP-группового сумматора (base-81) с симуляцией.

## 6. Статус интеграции
- Петя используется как советчик (не пишет код сам без контроля). Код/правки — от субагентов/MultiTool, Петя — ревью/второе мнение/анализ.
- Обращение только по явной необходимости (модель грузит CPU/GPU локальной машины и требует большого max_tokens).
