# DESIGN: Чистое двоичное fp32 dot-ядро для xc7a200t — оценка и сравнение с троичным tf48

*Дата:* 2026-10-19 *Ветка:* 2ch-pipeline *Статус:* R&D / дизайн-оценка (не реализация)

**Вопрос:** стоит ли строить чистое ДВОИЧНОЕ IEEE-754 fp32 ядро dot product вместо текущего троичного TFloat48 (ELEM_FMT=0/2), и каким методом умножать мантиссы (DSP48E1 vs LUT/CARRY4 bit-serial/array)?

---

## 0. Резюме (вердикт)

1. **Метод умножения для xc7a200t — ДВА выигрышных пути, один откровенно лишний:**
   - **DSP48E1** — безальтернативный победитель по площади/латентности для **одиночных** 24×24 умножителей: 3 DSP на умножитель, латентность ~2–3 такта конвейера. При NUM_MAC=32 нужно всего 96 DSP (13% от 740). Но при NUM_MAC=32 параллельно это 96 DSP — **больше, чем тратит всё нынешнее ядро (0 DSP)**.
   - **Array multiplier на LUT/CARRY4** — выигрывает по DSP-бюджету (0 DSP) и даёт НАСТОЯЩУЮ параллельность (одно произведение за 1–2 такта конвейера), цена — много LUT (~1.5–2.5k LUT на 24×24) и критический CARRY-путь.
   - **Bit-serial (последовательный сдвиг-и-сложи)** — проигрывает ВСЕМ: при 24 последовательных шагах gives throughput 24× ниже при почти той же площади, что array. Подходит только для сверхмалокоричневых встраиваемых/низкочастотных сценариев, здесь — НЕ рекомендуется.

2. **Строить ли двоичное fp32-ядро?** — **Не стоит в качестве замены/проекта-приоритета.** Троичное tf48 (ELEM_FMT=0/2) уже MET и достаточно для целевых нейро/дот-задач. Двоичное fp32-ядро уместно только как **опциональный второй движок** для зона, где нужен ОБЯЗАТЕЛЬНЫЙ бит-к IEEE-754 (замена на существующих битстримах, контрольные суммы/пайплайны, точность при больших range). Оно не будет ни быстрее (по Fmax уткнётся в тот же 125 МГц чип), ни кардинально меньше по площади, чем троичное.

3. **Host-конверсия (уже решена) — ПРАВИЛЬНО.** Для нейросетей ~31-бит точности TFloat48 замещает fp32 практически без потерь; конвертеры вне ядра убрали корень over-util. Двоичное ядро не решает ту проблему, что решала host-конверсия.

4. **Минимальный план, ЕСЛИ строить двоичное ядро** — в §7.

## 2. Умножение мантисс 24×24: DSP48E1 vs array vs bit-serial

### 2.1 IEEE-754 fp32 умножитель — что нужно

- Разбор: знак (XOR), экспонента (E_a+E_b−127, 8+8 бит), мантисса 24 бит (1.мантисса с ведущей 1), умножение 24×24 → 48-бит продукт, нормализация (сдвиг на 1 если старший бит слетел), округление (round-to-nearest-even, ~8-бит LZA + sticky).
- Суммарно готовый fp32-умножитель: **множитель мантисс + эксп-сумматор + нормализация/округление**. Округление — отдельная стоимость (~200–400 LUT + shift).

### 2.2 Вариант А — DSP48E1 (классический)

**Структура 24×24 через 18×18 DSP48E1:**
Декомпозиция 24 = 16 + 8 (или 18+6):
```
a*b = (a_hi·2^8 + a_lo) · (b_hi·2^8 + b_lo)
    = a_hi·b_hi·2^16 + (a_hi·b_lo + a_lo·b_hi)·2^8 + a_lo·b_lo
```
- Частичные: `16×16` (в 18×18 ok), `16×8`, `8×16`, `8×8`.
- **3 DSP** на произведение: 16×16 в DSP1, 16×8 и 8×16 — в один DSP через pre-adder (`P = (A+D)·B` две независимые 18-бит половины) или два DSP, `8×8` — в LUT (дёшево) или 4-й DSP.
- При **скомбинированном** варианте (pre-adder в DSP48E1: `A·B + D·B = B·(A+D)`) удаётся ужать 24×24 до **2–3 DSP** на умножитель.
- Латентность DSP48E1 умножения: **M→P = 3 такта** максимальный конвейер (может быть 1–2). Цепочка DSP (каскад) добавляет 1 такт/ступень.

**Итог (одиночный 24×24 мантисс-умножитель):**

| Метрика | DSP-путь (3 DSP) |
|---|---|
| DSP48E1 | **3** (0.4% бюджета) |
| Доп. LUT (норм+округл) | ~300–400 |
| CARRY4 | ~мл (только нормализация) |
| Латентность конвейера m.p. | 2–3 такта |
| Fmax | очень высокий (DSP быстрый, типично 300+ МГц) |
| Полный fp32 умножитель (с norm/round) | ~5–6 тактов конвейера |

### 2.3 Вариант Б — Array multiplier на LUT/CARRY4

Параллельная решётка partial product (24×24), суммация Wallace/Dadda или сложением строк через CARRY4.

| Метрика | Array (LUT/CARRY4) |
|---|---|
| LUT | **~1500–2500** (24×24; ~24 строк × ~24 бит AND-в-частичные + 2× сжатие) |
| CARRY4 | ~500–900 (суммирование) |
| DSP | 0 |
| Латентность | 1 произвед — может быть **1 такт конвейер** при полной пипелизации; combinational ~15–20 нс |
| Fmax | упирается в CARRY-строку; при глубокой пипелизации 150–250 МГц, НО критический путь длинный |
| Плотность | малая: 24×24 занимает ~1.5% LUT, но 32 умножителя = ~48–80k LUT |

**Ключевое ограничение:** при NUM_MAC=32 параллельных array-умножителей расход LUT = `32 × ~2000 = 64k LUT` — **~48% всего чипа только на умножение**, плюс дерево суммирования. Троичное ядро целиком 49k LUT. Это делает array-путь при полном распараллеливании НЕэффективным.

### 2.4 Вариант В — Bit-serial (shift-and-add, N тактов на бит)

| Метрика | Bit-serial (сдвиг-и-сложи) |
|---|---|
| LUT | ~600–1000 (одна строка partial-accum, управление 24×24) |
| DSP | 0 |
| Латентность | **24 такта** на одно 24×24 (последовательно по битам мультипликанда) |
| Throughput | **24× ниже** чем 1/такт; для 32 умножителей — 32 потока конвейерно могут перекрыться, но каждый выплюнет результат раз в 24 такта |
| Fmax | высокий (короткие пути, простой сдвиг+сложение) |
| Назначение | ультра-малоресурсные, длинные/низкочастотные потоки |

Bit-serial проигрывает array по throughput в 24× при схожей площади и проигрывает DSP по всем статьям кроме нулевого DSP. **Не рекомендуется** для NUM_MAC-параллельного dot на этом чипе.

### 2.5 Сравнительная таблица (одно 24×24 мантисс-произведение)

| Подход | DSP | LUT | CARRY4 | Латентность (конвейер) | Throughput (в/такт) | Fmax-риск | Вердикт |
|---|---|---|---|---|---|---|---|
| **DSP48E1** (3 DSP) | 3 | ~350 | ~30 | 2–3 такта | 1 (пипел.) | низкий | **ПОБЕДИТЕЛЬ** для одиночного |
| **Array LUT/CARRY4** | 0 | ~2000 | ~700 | 1 такт (пипел.) | 1 | средний (CARRY-путь) | хорош, если DSP дефицит |
| **Bit-serial** | 0 | ~800 | ~50 | 24 такта | 1/24 | низкий | **не рекомендован** |

**Вывод:** для **одиночных параллельных умножителей** DSP-путь даёт в ~2–3× меньше LUT и в разы лучше при 3 DSP × NUM_MAC. DSP-путь выбирается, если готовы потратить `3×NUM_MAC` DSP и нужна высокая throughput на умножитель. Array-путь выбирается при дефиците DSP / желании 0-DSP ядра (в духе текущего троичного).

## 3. Полное двоичное fp32 dot-ядро: ресурсы

### 3.1 Архитектура

Параллельность по NUM_MAC идентична троичной:
`NUM_MAC × fp32умножитель` → `дерево fp32-сумматоров (ADDERS barrel)` → `аккумулятор long-dot` (до 512 элементов).

### 3.2 Сценарий NUM_MAC=32, ADDERS=4

**Подход DSP (3 DSP/умножитель):**

| Ресурс | Расчёт | Итого | % xc7a200t |
|---|---|---|---|
| LUT (умножители, норм/округл) | 32 × ~350 | ~11.2k | 8% |
| LUT (дерево ADDERS=4 fp32-add) | fp32-add ~300–500 × дерево | ~4–8k | 3–6% |
| LUT (аккумулятор long-dot) | ~1k | ~1k | <1% |
| LUT (контроллер/FIFO/инфра) | ~5–8k (как в tdot_axi4) | ~6k | 4% |
| **LUT итого** | | **~22–27k** | **16–20%** |
| **DSP48E1 итого** | 3×32 = 96 (+бордюр) | **~96–100** | **13%** |
| FF | ~1.5×LUT | ~35–45k | 13–17% |
| BRAM | 1 FIFO + буферы | 2–4 | <1% |
| CARRY4 | дерево сумм | ~4–8k | 12–24% |
| Fmax | DSP+пипел | **125–200 МГц** | доходит легко |

**Подход array (0 DSP):**

| Ресурс | Расчёт | Итого | % |
|---|---|---|---|
| LUT (умножители 32×~2000) | 32 × 2000 | **~64k** | **48%** |
| LUT (дерево + аккум + контроллер) | | ~12k | 9% |
| **LUT итого** | | **~76k** | **~56%** |
| CARRY4 | решётки+суммы | ~25–30k | 74–90% ← **перегруз** |
| DSP | | 0 | |
| Fmax | CARRY-пути | 125 МГц (риск) | |

**Array-путь при NUM_MAC=32 НЕ реалистичен:** ~76k LUT (56%) + CARRY4 ~80% — упадёт в route/congestion как троичный 32/16. Array-путь мыслим только при NUM_MAC=8–16 (16×2000=32k LUT, CARRY4 ~35–45%) и тогда он конкурентоспособен с DSP-путём по LUT, но всё равно проигрывает по CARRY-напряжению.

### 3.3 Латентность dot

- DSP-путь: mul ~5–6 тактов (с norm/round) + дерево (ADDERS=4, NUM_MAC=32) ~8–12 тактов + аккум ~6 = **~20–25 тактов/чанк**.
- При NUM_MAC=32, плодительность ~1 чанк/25 тактов, 125 МГц → **~5 Mdot/с** (чанков 32-пар/с). Против троичного (dot~107 тактов @32/4, ~1.2 Mdot/с) — **двоичное быстрее по цикловой задержке ядра**, благодаря параллельным DSP вместо последовательных LUT-умножителей.

**Важно:** в полном tdot_axi4 узкое место — не ядро, а **AXI/DDR3 пропускная способность** (чтение N пар, PACKED6 6Б/эл). Ядро при 125 МГц не bottleneck: троичное ядро уже простаивает под памятью. Ускорение ядра 107→25 тактов НЕ даст ускорения сквозной задачи — упрётся в DDR3.

## 4. Сравнение с троичным tf48-ядром

| Критерий | Троичное tf48 (ELEM_FMT=0/2) | Двоичное fp32 (pure IEEE-754) |
|---|---|---|
| Точность мантиссы | ~31 бит (20 тритов × log2(3)≈31.7) | 24 бит |
| Диапазон | ~[8e-20, 3.6e19] | ~[1e-38, 3.4e38] (шире в ~10^19 раз) |
| LUT (NUM_MAC=32/4) | ~49k (36%) | ~22–27k (16–20%) DSP-путь |
| DSP | **0** | ~96–100 (DSP-путь) / 0 (array-путь) |
| Цикл dot (32/4) | ~107 тактов | ~20–25 тактов |
| Fmax | 125 МГц (MET) | 125–200 МГц |
| Конвертеры в ядре | НЕТ (0/2) | НЕТ (нативные fp32) |
| Точность для нейросетей | достаточно | избыточна |
| IEEE-754 бит-совместимость | нет | **да** (если нужна) |
| Over-util риск | нет (MET) | низкий (DSP-путь) / высокий (array 32) |

**Ключевые скорости/площади:** двоичное ядро на DSP компактнее по LUT (±4×), нулевой CARRY-перегруз, быстрее по циклу ядра. НО:
- троичное уже **MET** и уже ВЛЕЗАЕТ — нет текущей проблемы, которую двоичное решает как "фикс".
- Двоичное требует 96 DSP или (array) 56% LUT — давление на ресурсы, которого сейчас нет.
- **Оба ядра упрутся в память**, а не в ядро — быстрее ядро ≠ быстрее задача.

## 5. Host-конверсия vs двоичное ядро

Host-конверсия fp32→tf48 (решили ранее) — **единственно правильное** для целевой задачи:

1. **Точности TFloat48 хватает для нейросетей:** ~31 бит мантиссы против 24 у fp32 — точность ВЫШЕ fp32; диапазон [8e-20, 3.6e19] покрывает типичные веса/активации/промежуточные суммы. Для дот-произведений и ML-выводов потеря потерь ~нет.
2. Конвертеры УБРАНЫ из ядра → корень over-util (1.34M LUT) устранён; ELEM_FMT=0/2 MET.
3. Двоичное fp32-ядро НЕ решает fp32-проблему — она и так решена конверсией на хосте за 0 железо.

**Когда двоичное fp32-ядро реально лучше:**
- обязательная **бит-в-бит IEEE-754** совместимость (замена существующего fp32-пайплайна, верификация против host, гетерогенный обмен результатами);
- применение с **большим диапазоном** за пределами ~3.6e19 (fp32 шире на ~19 порядков);
- библиотечный fp32-движок, а не конкретный ML-профиль.
- (и если эти требования есть, то на чипе с 740 DSP это дёшево по LUT.)

В противном случае — троичное tf48 достаточно.

## 6. Рекомендация: DSP vs bit-serial (итог)

- **DSP48E1** — методика №1: 3 DSP/умножитель, ~2–3 такта конвейера, минимальный LUT, Fmax легко. 740 DSP чипа позволяют до ~240 параллельных 24×24 мантисс-умножителей — запаса на NUM_MAC до 2 цифр.
- **Array (LUT/CARRY4)** — единственный разумный 0-DSP путь, но при NUM_MAC≥16 думать о congestion (CARRY4/route). Конкурентоспособен только NUM_MAC≤16.
- **Bit-serial** — отклонить для этого сценария (24× throughput-проигрыш).

**Вывод:** для двоичного fp32 ядра на xc7a200t — **классический DSP48E1-путь** (3 DSP на 24×24, norm/round в LUT).

## 7. Вердикт и минимальный план (если строить)

**Вердикт:**
- (а) **Метод умножения: DSP48E1** (3 на 24×24). Bit-serial отбросить. Array — только для мало-ресурсного варианта.
- (б) **Строить двоичное fp32-ядро НЕ приоритетно.** Троичное tf48 (ELEM_FMT=0/2) достаточно, MET, 0 DSP. Переход оправдан ТОЛЬКО если нужен бит-IEEE-754 или широкий диапазон. Host-конверсия остаётся стандартным путём.
- (в) Если строить — DSP-путь, ресурсы ~22–27k LUT + ~96 DSP, Fmax 125–200 МГц, цикл dot ~20–25 тактов.

### Минимальный план (R&D макет, если строите)

1. **Standalone fp32-mul IP**: 24×24 мантисс через 3× DSP48E1 (+8×8 в LUT или 4-й DSP), pre-adder combo, конвейер 5–6 стадий, RNE-округление. Проверить в xsim против C-like reference (бит-в-бит).
2. **fp32-add (нормализация-суммирование-округление)** standalone, конвейер ~6–8 стадий, 0-DSP или частичный.
3. **compute_dot_par_fp32** — NUM_MAC × fp32-mul + дерево fp32-add, ADDERS-параметризация как у троичного. Синтез: цель LUT≤30k, DSP≤120, WNS≥0@125MHz.
4. **fp32_acc (long-dot)** на базе tfadd48-подобной обёртки над fp32-add; аккумуляция до 512.
5. **ПРИМЕЧАНИЕ по памяти:** fp32 = 4 байт/элемент (как ELEM_FMT=1), но БЕЗ конвертеров в ядре — данные уже нативные fp32. Это тот же формат-геометрия, что упущенный fp32-режим, но без LUT-взрыва.
6. Сопоставить с троичным: по сквозной задаче (DDR3-bound) — сравнивать циклы LOAD+COMPUTE, а не только ядро.
7. Если бит-совместимость не обязательна — **не строить**, остаться на tf48.

### Рабочий successor-порядок, если решите строить (по приоритету):

| Шаг | Артефакт | Ресурс-цель | Верификация |
|---|---|---|---|
| 1 | `f32_mul_pipe.sv` (3 DSP + RNE) | 3 DSP, ~350 LUT | xsim vs ref |
| 2 | `f32_add_pipe.sv` | ~400 LUT | xsim vs ref |
| 3 | `compute_dot_par_fp32.sv` (NUM_MAC/ADDERS) | 32/4 ≈ 22–27k LUT, 96 DSP | бит-в-бит |
| 4 | `f32_acc.sv` long-dot | ~1k LUT | tfadd48-эквивалент |
| 5 | `tdot_axi4_f32` (ELEM_FMT=3: нативный fp32, 4Б/эл, без конвертеров) | +инфра | полный AXI-стенд |

*Параметры троичного ядра (для сверки):* `tfmul_raw` pure-LUT (0 CARRY4): по 1 LUT6/бит на колонку carry-save, ~20 тактов финальной сборки; dot-латентность 32/4 ≈ 107 тактов (tree ~56); единственное узкое место троичного — конвертеры fp32→tf48 через `tf48_div_pipe` (~1.3M LUT), которые в ELEM_FMT=0/2 не инстанцируются (tdot_axi4.sv:273 gen_conv, dead-code при !FP32_MODE). Ресурсы троичного 32/4: ~49k LUT (36%), 36k FF, 1 BRAM, 0 DSP, WNS +0.185/+0.014.
