## 2. Дефекты по важности

### D1 — CRITICAL. Фикс в недостижимом классе; гейта `ALLOW_ENGINE_RESET` не существует

- Все рабочие пути (`ring_check.py:32-33`, `mailbox_check.py:44-45`, `device_prog_run.py:46-47`, `fpga_backend.py:111-112`) работают с `XdmaWinDma` (`test_dma_win.py:58`), у которого нет ни `read_config`, ни `write_config`, ни `engine_stalled`, ни `soft_reset_engine`.
- Вызовов новых методов нет вообще (`grep engine_stalled|soft_reset_engine` → только `xdma_driver.py:570,583,590`), поэтому даже на `XdmaWinUpstream` они не исполняются.
- Утверждение «используется ТОЛЬКО как фолбэк за флагом `ALLOW_ENGINE_RESET` (по умолчанию False)» (`xdma_driver.py:588-589`) — неверно: такого флага в репозитории нет.
- Важно: препятствия для порта нет. `XdmaWinDma` **уже** держит handle config-BAR (`test_dma_win.py:114`, `\control` = `bar[configBarIdx]`, `file_io.c:147-150`), а в этой сборке config-регистры и AXI-Lite живут в одном BAR0 (`ADDRESS_MAP.md:28,36,419`). Порт = `def read_config(...): return self._xfer(self._ctrl, False, offset, b"", length)` + симметричный `write_config`.

### D2 — CRITICAL. `BIT31` как «reset движка» не подтверждён и, скорее всего, не существует

- В дереве драйвера `XDMA_CTRL_RST` определён (`reg.h:74`) и **ни разу не используется**; собственный «сброс в idle» драйвера построен иначе — `EngineStop` (W1C RUN) + read-clear `statusRC` + перепривязка `firstDesc` (`dma_engine.c:1160-1183`).
- В PG195 v4.1 (версия IP плоской сборки: `block_design_top.tcl:145,742`; DFX-сборка использует 4.2 — `xdma_ddr3_bd.tcl:431`) поле **31:28** регистра *H2C/C2H Channel Control (0x04)* числится **Reserved** (docs.amd.com, PG195 ru/en, «C2H Channel Control (0x04)», «H2C Channel Control (0x04)»).
- Значит запись `0x80000000` — в лучшем случае no-op, в худшем — недокументированное поведение. Фикс построен целиком на этом бите.
- Предыдущий аудит пришёл к тому же: «драйвер не имеет ioctl на `XDMA_CTRL_RST` (bit31 `control`, `reg.h:74`); … это отдельное действие, вне read-only» (`AUDIT_HOST_DMA.md:108`), «`XDMA_CTRL_RST` не используется ни в одном пути отмены/восстановления» (`AUDIT_HOST_DMA.md:122`).

### D3 — CRITICAL. Последовательность записи портит конфигурацию канала и не восстанавливает её

`soft_reset_engine:592-593` пишет в `control` (0x04) значения `0x0`, затем `0x80000000`. Это:
- снимает RUN — но не через W1C, а перезаписью всего регистра;
- затирает IE-биты (1-6, 9-23), которые драйвер ставит **однократно** при инициализации (`dma_engine.c:285-290`) и больше не восстанавливает;
- затирает `NON_INCR_ADDR` (25) и `POLL_MODE` (26), которые драйвер меняет через W1S/W1C (`file_io.c:589-591`, `dma_engine.c:1708-1712`).

Итог: даже при рабочем bit31 канал останется без прерываний и с потерянным режимом адресации до перезагрузки драйвера. Для «только сброса состояния» следовало бы использовать `controlW1C` (0x0C) / `controlW1S` (0x08) — ровно как это делает сам драйвер (`reg.h:120-123`, `dma_engine.c:1149,1155,1171`).

### D4 — HIGH. Нет верификации результата и нет ожидания выхода из reset

- Не читается обратно RST-бит: если он не самосбрасывающийся, канал остаётся в reset навсегда — и все последующие DMA уйдут в таймаут до перезагрузки.
- Нет ожидания `BUSY=0` (`status` 0x40) с таймаутом; драйвер для приведения в idle ещё и читает `statusRC` (0x44, read-clear) — фикс этого не делает.
- `sleep(0.01)` после reset — единственная «синхронизация»; запись идёт через `WriteBarFromRequest` (`file_io.c:398`, posted write), без read-back flush.
- Возвращается `True` («сделано») при отсутствии каких-либо подтверждений — это ложное подтверждение успеха для вызывающего кода.

### D5 — HIGH. Сброс идёт мимо драйвера, который владеет движком

- Запись в config-BAR выполняется из user-mode, без координации с драйвером: его спинлоки, `isReqPending`/`txnDone`, watchdog (`dma_engine.c:513-521`) не знают о сбросе.
- Если сброс попадёт в момент активной C2H-транзакции, данные уже частично записаны в host-буфер запроса — драйвер завершит IRP как успешный/таймаутный с некорректным содержимым; для H2C возможна частичная запись в DDR3.
- Правильный порядок — только при отсутствии незавершённых транзакций (движок остановлен, IRP нет), иначе сброс = гарантированная потеря/порча транзакции.

### D6 — MEDIUM. Диагностика слабее доступной и «тихо» деградирует

- `status` (0x40) не читается, хотя константа `_X2C_H2C0_STAT` объявлена (`xdma_driver.py:567`) и не используется нигде → мёртвая константа; BUSY/ошибочные биты (`reg.h:82-95`) могли бы отличить «BUSY залип» от «ждём дескриптор».
- Короткое чтение не проверяется: прогон с 2-байтовым ответом дал `True` (замороженный «счётчик»).
- Любое исключение → `False` без лога: недоступный config-BAR неотличим от здорового движка.
- `base` не валидируется: принимается любое значение, тогда как валидны 0x0000 (h2c_0) и 0x1000 (c2h_0) (`reg.h:112`, `dma_engine.c:694`). Проверка личности блока (`identifier` @ base+0x00, маска `XDMA_ID_MASK=0xFFF00000`, `XDMA_ID=0x1FC00000`, `reg.h:34-35`; эталон — `EngineExists`, `dma_engine.c:693-705`) отсутствует, поэтому `base=0x200` или `base=0x3000` молча прочитают чужой блок.
- Сравнение `n1 == n0` вместо `(n1 - n0) & 0xFFFFFFFF` (wrap 32-битного счётчика) — теоретический false-positive.

### D7 — LOW. Незавершённость по существу (и это надо писать явно)

Сброс без перепрограммирования канала — заведомо неполное восстановление:
`control` снят в 0 (RUN=0), `firstDescLo/Hi` не перепривязаны, `EngineStart` не выполнен, IE не восстановлены. Восстановить `firstDesc` из Python физически нельзя — это физический адрес `WdfCommonBuffer` драйвера (`dma_engine.c:96-98, 1175-1178`). То есть **сервис вернёт только следующий DMA-запрос через драйвер** (ProgramDma → ResetIdle → EngineStart), а текущая транзакция будет потеряна и завершится `STATUS_TIMEOUT` watchdog'ом. Формулировка в коде и в PR-описании должна говорить именно это, а не «канал останется нерабочим» (слишком сильно) и не «только сброс состояния» (слишком слабо — сбрасывается ещё и конфигурация канала).

### D8 — LOW. Мелочи API

- `write_config` не ограничивает область config-регистрами (0x0000-0x7FFF): `write_config(0x23000, …)` попадёт в регистры TDOT/GPIO того же BAR0 (`ADDRESS_MAP.md:419`), хотя докстринг обещает обратное.
- Имена `_X2C_H2C0_*` используются для обоих направлений через `base` — вводит в заблуждение (для `base=0x1000` это уже C2H0).
- `_X2C_CTRL_RST` — не смещение, а маска, в одном ряду с offset-константами.
- Асимметрия бэкендов: у `XdmaLinux` (`xdma_driver.py:102-200`) аналога нет вообще, т.е. на Linux-пути диагностики движка не будет.
- `struct.pack("<I", 0x0)` вместо `b"\x00" * 4` — не дефект, но шум.

## 3. Что подтверждено корректным (не переделывать)

1. **Layout регистров XDMA сверен и верен**: `control=0x04`, `status=0x40`, `completedDescCount=0x48`, `h2c_0=0x0000`, `c2h_0=0x1000`. Выход за `ENGINE_OFFSET/SGDMA_BLOCK_OFFSET` в фиксе не происходит.
2. **`engine_stalled` действительно read-only** и не трогает опасные регистры: `statusRC` (0x44) — read-clear (`reg.h:127`), `controlW1S/W1C` — write-only; фикс к ним не обращается. Проверено прогоном на заглушке.
3. **Нет рекурсии**, вызовы `read_config` соответствуют сигнатуре, `engine_stalled(base=base)` в `soft_reset_engine` передаёт аргумент корректно.
4. **Синтаксис/импорты** в порядке (`py_compile` OK), `close()`/`__del__` не задеты, поведение при `_ctl=None` безопасное (возврат `False`).
5. **Семантика признака «зависания» для этого драйвера в принципе верная**: RUN снимается на завершении/таймауте (`dma_engine.c:358, 1641`), поэтому `RUN=1 ∧ счётчик не растёт` — осмысленный индикатор для H2C0.
6. Вывод про необходимость перепривязки `firstDesc` после сброса — **верен** и подтверждён `dma_engine.c:96-98, 1092-1100, 1164-1167, 1175-1178`.

## 4. Вывод: годится ли фикс как есть

**Как есть — не годится, применять на плате нельзя.**

- Диагностическая часть (`engine_stalled`) — безобидна и полезна, но **недостижима** на используемом пути (D1) и слабее, чем могла бы быть (D6).
- «Исполнительная» часть (`soft_reset_engine`) — **опасна**: пишет в hardware-BAR мимо драйвера (D5), затирает конфигурацию канала (D3), опирается на недокументированный бит (D2), не проверяет результат (D4) и заведомо не завершает восстановление (D7). При этом к наблюдаемому зависанию (tdot read-master / `M00→MIG`) она неприменима (6.1) — там помогает только `reset_rtl_0`/перезагрузка (`SYNTHESIS.md:36`, `AUDIT_RTL_FSM.md:139`).

**Обязательно доработать до любого применения:**

1. **Перенести `read_config`/`write_config` в `XdmaWinDma`** (2-3 строки через существующий `self._ctrl` + `_xfer`, `test_dma_win.py:114,135`) либо вынести config-BAR доступ в общий миксин, которым пользуются оба класса. Без этого фикс не исполняется.
2. **Убрать/переименовать `ALLOW_ENGINE_RESET`** либо реально реализовать гейт (по умолчанию `False`) и залогировать отказ. Сейчас докстринг описывает несуществующую защиту.
3. **Не использовать BIT31 как reset**, пока не подтверждено (чтением `control` после записи на остановленном движке + PG195 для версии IP платы). Пока не подтверждено — `soft_reset_engine` должен либо отсутствовать, либо быть честно назван «экспериментальным, только с остановленным драйвером, требует подтверждения бита».
4. **Если reset остаётся** — минимум: проверка `identifier` блока (`base+0x00 & 0xFFF00000 == 0x1FC00000`), stop через `controlW1C` (0x0C), RST через `controlW1S` (0x08), read-back с проверкой самосброса, ожидание `BUSY=0` по `status` (0x40) с таймаутом, восстановление IE-битов, и `return False` при любой неверифицированной стадии. `True` только по факту подтверждённого состояния.
5. **Задокументировать реальное следствие резета**: восстановление произойдёт только следующим DMA-запросом через драйвер (перепривязка `firstDesc` в `XDMA_EngineResetIdle`), текущая транзакция будет потеряна и завершится `STATUS_TIMEOUT`.
6. **Усилить диагностику**: читать `status` (0x40) вместо мёртвой константы, проверять `len(read_config(...)) == 4`, логировать исключения, валидировать `base ∈ {0x0, 0x1000}`, считать `(n1 - n0) & 0xFFFFFFFF`.
