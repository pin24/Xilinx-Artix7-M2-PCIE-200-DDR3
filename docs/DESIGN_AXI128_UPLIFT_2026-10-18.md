# АРХИТЕКТУРНАЯ ОЦЕНКА: подъём C_M_AXI_DATA_WIDTH 64→128 в tdot_axi4

Дата: 2026-10-18, ветка `2ch-pipeline`, модель deepseek-flash.
Статус: **ДИЗАЙН-ДОКУМЕНТ (research + proposal)**. RTL не менялся. Синтез/железо не запускались.

---

## 0. Executive summary (для тех, кто прочтёт только этот раздел)

1. **Полный переход SW=8→16 (DW=128) НЕ даёт обещанного 2×.** Во всех трёх режимах
   узким местом является НЕ ширина AXI-шины, а **конвейер 1 элемент/такт** (load-BRAM,
   fp32-конвертеры, barrel packed6_rd). Удвоение шины сжимает только read-фазу, а
   load+compute фазы фиксированы на 1 элем/такт и идут ПОСЛЕДОВАТЕЛЬНО после чтения.
   Реальный выигрыш ≤ ~1.2× для легаси, ~1× для packed6, **0× для fp32** (fp32 и так
   шина-ограничен на уровне конвертера, не наоборот).

2. **fp32 (ELEM_FMT=1) не может выиграть в принципе**: `f32_to_tf48_pipe` — это
   ОДНОканальный byte-serial делитель, throughput строго 1 элемент/такт, ~27 тактов
   латентности. Даже при DW=128 и «4 fp32 за beat» конвертер всё равно берёт 4 такта
   на beat. Расширитель fp32 тоже выдает 1 элем/такт. Шина не является тут бутылочным
   горлышком.

3. **Большой внетерный блок** — хост-интеграция уже жёстко зашита на 64 бита:
   `xdma_ddr3_core_top.sv` (m_axi_wdata[63:0], rdata[63:0]) и BD SmartConnect S02
   (`M_AXI_TDOT`). Подъём до 128 требует **пересборки BD/MIG/SmartConnect** — это не
   RTL-параметризация и не проверяется xsim-офлайн.

4. **Реальный 2× возможен только вертикальным изменением** (шина+load 2 элем/такта+
   перекрытие read/load+compute) — это не «подъём ширины», а новая поточная структура.

5. **Рекомендация: ОТЛОЖИТЬ полный переход.** Единственная безопасная фаза — чистое
   xsim-исследование пропускной способности текущей архитектуры (замерить cnt_mem vs
   cnt_compute), чтобы подтвердить вышесказанное цифрами ДО инвестиций. Полная 128 —
   высокий риск сломать 128/128+98/98+34/34 верифицированных регрессий при нулевом
   практическом выигрыше.

## 1. Карта 64-бит зависимостей (до файл:строка)

Все координаты — ветка `2ch-pipeline`, состояние HEAD c3bf3ee.

### 1.1 Параметры-производные (переживут 128 автоматически)

| Локация | Что | При DW=128 |
|---|---|---|
| `rtl/integration/tdot_axi4.sv:160-163` | `localparam SW=DW/8`, `AXI_SZ=$clog2(SW)=3` | SW→16, AXI_SZ→4. Авто. |
| `:670` `M_AXI_ARSIZE=AXI_SZ` | ARSIZE | →4 (16B). Авто. |
| `:752` `M_AXI_AWSIZE=AXI_SZ` | AWSIZE | →4. Авто. |

Эти производные корректны сами по себе; проблема — НЕ в них, а во всей *семантике*
слова как «8 байт / 1 элемент» ниже.

### 1.2 Read-путь (самый аффектированный)

| Локация | Что | При DW=128 |
|---|---|---|
| `:690` `M_AXI_RREADY = r_ready_r && rd_ready_gate` | гейт RREADY | логика та же, ширина beat 16Б |
| `:1006-1009` (PACKED6) `fifo_wdata = p6_elem : M_AXI_RDATA[47:0]` | легаси-элемент = [47:0] | `M_AXI_RDATA[47:0]` всё ещё элемент; но «1 beat = 1 elem» НЕВЕРНО, beat=2 elem → нужно 2 записи fifo/beat |
| `:1061-1063` (fp32) `fifo_wdata = fp_beat_q[63:32] / {16'b0,M_AXI_RDATA[31:0]}` | расширитель beat | beat=128 → 4 fp32, текущий расширитель отдаст только 2 (младшая половинка) — потери |
| `:1073` (legacy) `fifo_wdata = M_AXI_RDATA[47:0]` | 1 elem/beat | beat=128 → теряется старший элемент слова |
| `:939-954` fp32-расширитель | `fp_beat_q[63:0]`, 1 beat→2 fp32 за 2 такта | нужен 4-элементный... но конвертер 1/такт → расширитель так и останется 2-тактовым на половинку |
| `:981-1048` rbuf (PACKED6) | `rbuf_mem[0:3]` по `[63:0]`, `rbuf_head`=головное слово, глубины 4 | слово→16Б (4×16=64Б); коллизии/глубина при прежнем к-использовании удерживаются, НО баррель рассчитан на 64-бит вход |

### 1.3 Barrel PACKED6 (rtl/block/packed6_rd.sv) — самый драматичный блок

| Локация | Что | При DW=128 |
|---|---|---|
| `:33` `parameter WORD_B=8` | байт в слове | →16 |
| `:39` `input logic [63:0] wdata` | AXI-RDATA | →127:0 |
| `:44` `input logic [2:0] start_skip` | 0,2,4,6 | для 16-байт слова смещения до 15 → `[3:0]` |
| `:54` `logic [95:0] sr` | буфер необработанных байт (12) | нужно ≥ 22 байта (16+остаток) → `sr[175:0]`? |
| `:55` `logic [3:0] nbytes` | 0..12 | 0..22 → `[4:0]` |
| `:64` `emit_can = (nbytes>=6) && emitted<n_elem` | критерий эмита | то же, но 16-байт слово даёт 16/6≈2.67 элементов → частичный 2-й/3-й элемент |
| `:104-121` `unique case(nbytes)` на {0,2,4} | наложение слова | при 16Б слове остаток ∈ {0,2,4,6,8,10,12,14} → 8 веток case, все константы пересчитаны |
| `:91-100` (armed-ветка) `wdata >> start_skip*8`, `nbytes<=8-skip` | первое слово | 16-skip, ширина сдвига 128 |

**Ключевой момент:** при NUM_MAC=32, 6·32=192 байт = ровно 12×16-байтных слов (выровнено),
и skip следующего прохода `elems_done*6 mod 16` = 0 для elems_done кратного 8. То есть
при NUM_MAC=2^k (k≥3) PACKED6 становится *почти чистым*: все слова полные, скипы нулевые.
НО оно кратно лишь потому, что 6·32 = 192 % 16 == 0. Хрупкая реализация: при NUM_MAC=8
(6·8=48%16=0 тоже) ок; при NUM_MAC=16 (96%16=0) ок; NUM_MAC=4 (24%16=8) ломается.

### 1.4 Write-путь

| Локация | Что | При DW=128 |
|---|---|---|
| `:694` `logic [DW-1:0] w_data_r` | WDATA | авто широкий |
| `:695` `logic [SW-1:0] w_strb_r` | WSTRB | 16 бит |
| `:704` `logic [DW-1:0] wr_data` | данные записи | авто |
| `:705` `wr_strb_q[SW-1:0]` (GAP-2 рег.) | WSTRB на старт | авто |
| `:1334/1377` `wr_data <= {16'h0, core_result}`; `:1407` `{32'h0,t2f_m_data}` | результат — 8Б слово | результат легаси/packed6 = 6Б, fp32=4Б; при SW=16 слово шире, WSTRB покрывает только нижние 6/4 байта → корректно, НО адрес result должен быть 16-байт-выровнен (align_q!), это ужесточение |
| `:1424,1433` completions `comp_base+rptr*16 (+ SW)` | 16-Б completion | при SW=16 completion «2×64b» становится 32Б → ЛОМАЕТ host-контракт (дескрипторы 4×64, completion 2×64 = в 16-бит словах становится иначе) |

### 1.5 4KB-кламп (AXI4 A4.3.1)

| Локация | Что | При DW=128 |
|---|---|---|
| `:1496` `ar_addr_w = rd_addr + rd_issued*SW` | байтовый адрес следующего beat | SW=16, формула корректна по байтам |
| `:1497-1499` `bnd_bytes_w = 13'h1000 - {1'b0, ar_addr_w[11:0]}`; `bnd_words_w = bnd_bytes >> AXI_SZ` (с clamp ≥1) | длина до 4KB в СЛОВАХ | AXI_SZ=4 → слова по 16Б; кламп по 16-байт словам, spec соблюдён (не пересекаем 4KB). Формально рабочая, НО: 4KB%16==0, 4KB%8==0 — на 8-байт границах кламп раньше не перескакивал; на 16-байт остаток до границы может быть 0 (ровно на границе) → надо аккуратно clamp ≥1, уже есть |
| `:1503` `ar_len_w = min(len_full, bnd_words-1)` | кламп burst | зависит от AXI_SZ корректно |

Кламп по байтам — минимально меняется. Главный вопрос — не кламп, а то, что `rd_total`
это число СЛОВ, и при SW=16 элементный `words_fn`/`words_skip_fn` (`:185-206`) считают
слова в 64-битной логике (`*8`/`>>3`), а при 128 должны делить на 16 — **все функции
количества слов надо переписать под битность**, включая предвычисление `next_words_q`
(`:845-857`).

### 1.6 Планировщик / дескрипторы

| Локация | Что | При DW=128 |
|---|---|---|
| `:1183-1185` `rd_total<=32'd4`; fetch 4 слов | дескриптор 32Б = 4×64b | при 16Б слове «4 слова» = 64Б, а дескриптор 32Б = 2 слова. Считывается лишнее/половина. Нужен отдельный тип перечисления |
| `:1421-1451` CS_CMP1/2/3 completion | 2×64b=16Б | при SW=16 completion = 1 слово → структура записи и смещения rptr*16 ломаются |
| `:805-824` нормализация n_total | не зависит от ширины | ок |

Все scheduler-структуры завязаны на «слово=8 байт» (64-битные регистры `desc_w[4]`, `[63:0]`). **Планировщик — отдельный аффектированный пласт**, ортогональный данным.

### 1.7 Load-конвейер (не AXI, но лимитер пропускной способности)

| Локация | Что | Примечание |
|---|---|---|
| `:539-580` FIFO 48-бит, push 1/такт | сборка элементов в BRAM | 1 элем/такт — потолок питания |
| `:1264-1310` CS_LOAD (легаси) 2-стадийный BRAM-конвейер | 1 слот/такт = 1 элем/такт | НЕ вырастет сам по себе при 128 |
| `:1279-1286` fp32-CS_LOAD через F2T | 1 элемент F2T/такт | потолок = конвертер |

## 2. Анализ «сложных мест» при DW=128

### 2.1 fp32-расширитель (`:941-954`)
- Вариант «4 fp32 за 4 такта» из одного beat 128: текущий `fp_beat_q[63:0]` захватывает
  только младшие 64 бита → при DW=128 расширить до `fp_beat_q[127:0]`, отдавать по 32 бита
  за такт (`fp_beat_q[31:0]`, `[63:32]`, `[95:64]`, `[127:96]`), `fp_exp_busy` держать 4 такта.
  Расширитель — тривиальный mux, переписать легко.
- **НО**: получатель — F2T (1 элем/такт). Расширитель ускоряется, а конвертер нет.
  Класть 4 fp32 в FIFO быстрее нельзя — fifo_pop в CS_LOAD тоже 1/такт,
  и `pop_lim=chunk_words*2` (`:1482`) рассчитан на 2 половинки/beat.
- **Вывод: fp32 не выигрывает от 128.** Относительная сложность переделки — низкая,
  но бесполезная.

### 2.2 barrel packed6_rd (самый дорогой блок)
- Полностью переписать: `sr` до ≥176 бит, `nbytes` 5 бит, `start_skip` 4 бита,
  8 веток `case(nbytes)`, `WORD_B=16`. Каскад сдвигов 176-бит НЕ тривиален и
  **вероятно ударит по таймингу — ровно тот путь, который мы только что развязали**
  реестровым rbuf (commit 0a06327) и 2-стадией next_words (c3bf3ee).
- Если NUM_MAC=32/16/8 и 6·NUM_MAC%16==0 → скипы нулевые, слова полные — структуру
  можно упростить (два элемента + полуслово), но LUT-плотность и 176-бит сдвиг всё
  равно добавляют уровень комбинаторики. **Риск регресса таймингов, которые уже в
  зеленой зоне.**
- Unit-тест `verify_packed6_rd.py` заточен на 64-бит вход (skip∈{0,2,4,6}, WORD_B=8).
  Придётся параметризовать или завести отдельную модель 128.

### 2.3 rbuf (PACKED6 staging)
- Слова 4×64 → 4×128 (64 байта). Механика указателей/глубины (wptr!=rptr запас, глубина 4,
  `rbuf_room_q` с 1 слотом запаса) переносится ДОСЛОВНО при смене ширины шины слова.
  Относительная сложность переделки — низкая. Риск коллизий не растёт (логика от
  ширины байта не зависит).

### 2.4 4KB-кламп
- Минимальные правки (AXI_SZ авто). Формально spec-безопасен при 16-байт словах.
  Сложность низкая.

### 2.5 Write + align
- `align_q` (`:1161-1166`, `:1221-1226`) сейчас требует выравнивания 8 (легаси/packed6)
  / 4 (fp32) байт. При SW=16 каждый beat покрывает 16 байт → легаси-элемент или
  результат должен лежать в 16-байтном слове с НУЛЕВОГО смещения, иначе частичный
  first-beat (старшие байты раньше адреса) повредит соседей. Это **ужесточение
  выравнивания до 16 байт** для legacy/packed6-результата и фактически ломает
  легаси-раскладку «элементы по 8 байт с шагом 8»: 2-й элемент попадает во старшее
  слово 16-байта → требует 2 элемента за beat с корректным чередованием, а не
  произвольного начала.

### 2.6 BURST_RD_LEN
- Сейчас 32 слов × 8Б = 256Б/AR. При 128: 32 слов × 16Б = 512Б/AR — пересчитать MPS
  (макс. длина burst в байтах) под DDR3: 512Б burst превышает 256Б типичного предела
  для некоторых MIG-конфигураций → может понадобиться `BURST_RD_LEN=16` при DW=128,
  что частично съедает выигрыш по числу beats (но полнее по байтам).

### 2.7 Scheduler / descriptors
- Полный пересчёт «слов» → дескриптор займёт 2 слова (32Б/16), completion 1 слово (16Б/16).
  Затрагивает `desc_w[4]`, `rd_total=4`, комплет-смещения `rptr*16`, `+SW`. Отдельный пласт
  с host-контрактными последствиями.

## 3. Оценка целесообразности (получим ли 2×)

### 3.1 Фазовый состав задачи (документированная последовательность, не конвейер)
```
read(data) → read(weights) → load → compute → (accum → next pass) / (write result)
```
Фазы **следствуют, не перекрываются** (см. контроллер `:1235-1451`). Только read-фаза
чувствительна к ширине шины; load и compute фиксированы по числу элементов.

### 3.2 Сколько даёт удвоение шины (оценка циклов на один проход, NUM_MAC=32)

| Режим | read (DW=64) | load | compute | read (DW=128) | Итог 128/64 |
|---|---|---|---|---|---|
| легаси (8Б) | 64 beats + lat | 64 (1 элем/такт) | ~40 | 32 beats + lat | **~1.2×** (не 2×) |
| fp32 (4Б) | 32 beats, но расширитель+F2T 1 элем/такт ⇒ 64 мин | 64+27 | ~40 | те же 64 мин (конвертер-лимит) | **~1.0× (0×)** |
| PACKED6 (6Б) | 48 beats, barrel 1 элем/такт ⇒ 64 мин | 64 (barrel 1/такт) | ~40 | те же 64 мин (barrel-лимит) | **~1.0× (0×)** |

Легаси выигрывает только read-фазу, которая даже на 64-бит занимает не всё время.
fp32 и packed6 полностью ограничены конвейерами 1 элем/такт — удвоение шины ничего
не даёт (они уже шину-недогружают).

### 3.3 Почему это так
- Load (`CS_LOAD` BRAM 1 слот/такт, легаси `:1287-1309`) и конвертеры (f32_to_tf48 div
  `f32_to_tf48_pipe.sv`, 1 элем/такт, 27 такт латентности) и barrel (`packed6_rd`
  emit 1/такт) — **все узкие места вне шины**.
- Даже если прочитать в 2× быстрее, данные лягут в FIFO (1 запись/такт, `:573-580`) и
  будут вычитываться load-конвейером по 1/такт.
- Реальный 2× требует РАСШИРЕННОЙ перестройки: load 2 элем/такт + параллельные F2T
  (нереально, делитель один) + перекрытие read//load + compute в конвейере. Это
  новая архитектура, а не «поднять ширину».

### 3.4 Внетерный блок — хост/BD
- `rtl/integration/xdma_ddr3_core_top.sv:94,100` — `m_axi_wdata[63:0]/rdata[63:0]` жёстко
  64. BD `M_AXI_TDOT` → `xdma_axi_smc` S02. Смена на 128 = **пересборка BD/MIG/SmartConnect/
  XDMA-канала**, regenerирование IP. НЕ проверяется xsim, риск интеграции высокий.
- `axi_aclk_out` комментарий самого топа (`:216`) говорит «128-бит» про XDMA-канал —
  но путь tdot→SMC→MIG зашит 64 в обвязке.

### 3.5 Влияние на режимы — НЕсимметричное
- **Легаси**: единственный, кто хоть что-то выиграет на read-фазе (но ≤ 1.2×), при этом
  ломается 8-байт раскладка памяти и планировщик.
- **fp32**: выигрыш 0, регресс-pиск на расширитель + align.
- **PACKED6**: выигрыш 0 (barrel-лимит), максимальная переделка RTL (176-бит barrel),
  риск таймингов.
- **Все**: ломается host-контракт планировщика и память-лейаут.

## 4. План (if / когда решат делать после замера)

### 4.1 Минимально-инвазивная фаза (рекомендуемая, МОЖНО в рамках xsim)
**НЕ менять SW на 16.** Вместо этого — измерительная фаза подтверждения:
1. Прогнать текущий 64-бит битстрим/симуляцию с OBS и замерить `cnt_mem` vs `cnt_load`
   vs `cnt_compute` (`OBS: 0x78-0x84`, документировано в `docs/OBSERVABILITY.md`).
   Это даст ФАКТИЧЕСКОЕ распределение времени по фазам и ответ, насколько read вообще
   доминирует. Без этих цифр любой «двойной» план — гадание.
2. (Опционально, чисто xsim) Построить экспериментальную модель read-фазы DW=128 на
   легаси и прогнать `tb_tdot_axi4`, чтобы увидеть, сжимается ли read-время настолько,
   чтобы оправдать переделку. НЕ трогая прод RTL — копия.

### 4.2 Полный переход SW=16 — модули, которые менять (если замеры оправдают)

**Параметризовать / переписать:**
- `rtl/block/packed6_rd.sv` — параметризовать `WORD_B` число байт слова (8/16): ширина
  `wdata`, `sr`, `nbytes`, `start_skip`, `case(nbytes)`-ветки, `drained`. Добавить
  compile-time `if (WORD_B==16)` блок, оставить 8-бит полностью нетронутым (для регрессий).
- `rtl/block/packed6_wr.sv` — параметризовать `SW` (уже есть) → `woff` ширина `[2:0]`→`[3:0]`,
  `wdata[63:0]`→`[DW-1:0]`. Лёгкий.
- `rtl/integration/tdot_axi4.sv` — главный файл:
  - `words_fn`/`words_skip_fn` (`:185-206`) и префетч `next_words_q` (`:845-857`) —
    заменить жёсткий `*8/8`/`>>3` на `/SW` по байтам (байтовый учёт, не словно-битность).
  - read-поток gen_fifo_* : легаси «beat→2 elem» (fifo по 2 записи), fp32 расширитель
    `fp_beat_q[127:0]` + 4-тактовый `fp_exp_busy`, packed6 через параметризованный barrel.
  - load-конвейер CS_LOAD (`:1264-1310`): опционально 2 элем/такт (иначе нет смысла).
  - align_q `:1161-1166,1221-1226` — выравнивание до 16/4 в зависимости от режима.
  - планировщик: desc 2 слова, completion 1 слово, смещения rptr.
- `rtl/integration/xdma_ddr3_core_top.sv` — порт m_axi_wdata/rdata 128 + ребилд BD
  (SmartConnect/MIG/XDMA S02). Верхнеуровневый, вне xsim.

**Можно оставить (по-сути width-агностично):**
- FIFO 48-бит (`:539-580`) — элементная, не широтная. ОК.
- аккумулятор tfadd48, compute_dot_par_raw, конвертеры (f32_to_tf48/tf48_to_f32) — элементные.
  Конвертеры ОСТАЮТСЯ лимитером fp32 в любом случае.
- регистровая карта AXI-Lite, OBS — не зависят от DW.
- rbuf (глубина/пойнтеры) — логика переносится при смене ширины слова; менять только ширину `rbuf_mem`.

### 4.3 Тестовые верификаторы — что обновить
- `rtl/block/verify_packed6_rd.py` — параметризовать WORD_B; прогон для 8 (регресс) и 16 (новый).
- `rtl/integration/tb_tdot_axi4*.sv` и `verify_tdot_axi4_{packed6x,fp32x,fp32}.py` —
  модели памяти 64→128 (адреса `>>3`→`>>4`, WSTRB до 16), плюс НОВЫЙ DUT-параметр `C_M_AXI_DATA_WIDTH=128`
  для интеграционного tb. Регресс 64-бит оставить как отдельный конфиг, чтобы не ломать 128/128+98/98+34/34.
- Новый unit для fp32-расширителя 128 (4 половинки за 4 такта).
- Scheduler tb (`verify_planner/tb_tdot_sched*.sv`) — дескрипторы/completion под SW=16.

## 5. Риски и рекомендация

### 5.1 Риски
1. **Регресс верифицированных 64-бит регрессий** (128/128 packed6x, 98/98 fp32x,
   34/34 barrel, 4/4 легаси/fp32). Любая параметризация, затрагивающая общие пути
   (особенно `words_skip_fn`, load-конвейер, планировщик), рискует сломать общий код
   даже при сохранении DW=64 по умолчанию. Нужны compile-time guards `if(DW==128)`.
2. **Тайминговый регресс**: 176-бит каскад сдвигов barrel и, при желании, 2 элем/такт
   load — оба могут вернуть критические пути, которые мы только что гасили
   (rbuf 0a06327, next_words c3bf3ee). XDC/ресинтез пришлось бы повторять.
3. **Host/BD-контракт**: пересборка BD + смена ширины S02 — самый рискованный и
   непроверяемый офлайн шаг; 128 на стороне SmartConnect может потребовать данных
   раскореллировать MIG/BRAM.
4. **Несимметрия режимов**: даже успешный 128 даёт ~0 для fp32/packed6 — инвестиция
   окупает только легаси-путь и только отчасти.

### 5.2 Рекомендация
**ОТЛОЖИТЬ полный переход.** Обоснование:
- Архитектурный выигрыш 2× упирается не в ширину AXI, а в 1-элементные конвейеры
  (load/fp32-conv/barrel) и в последовательность read→load→compute. Удвоение шины без
  вертикальной перестройки даёт ≤1.2× (легаси), 1× (packed6), 1× (fp32).
- Стоимость/риск (RTL barrel+load+planner+BD+регессии+тайминги) многократно превышает
  ожидаемую пользу.
- **Сначала**: бесплатная измерительная фаза на текущем 64-бит битстриме через OBS
  (`cnt_mem`/`cnt_load`/`cnt_compute`). Если read фаза займёт, скажем, ≥60% времени и
  есть запрос именно на легаси/memory-bound сценарий — тогда частичный вариант «128
  только для легаси, параллельно 2 элем/такт load» под пилотным флагом.

**Предлагаемый частичный вариант (если замеры оправдают):**
- Реализовать `DW=128` ТОЛЬКО под ELEM_FMT=0 (легаси) с 2 элем/такт load, остальные
  режимы держать 64. Это изолирует риск fp32/packed6 и даёт единственно возможный 2×
  (легаси memory-bound). Планировщик/BD всё равно потребуют переделки — включить
  только после измерительной фазы.
