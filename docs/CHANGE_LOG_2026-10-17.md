# CHANGE LOG — 2026-10-17 (BSOD 0x10D_4 при перекрытии W+R, фикс EvtCancelDma)

Каталог: `C:\A7_M2\Xilinx-Artix7-M2-PCIE-200-DDR3` (main).

## 1. Инцидент
При запуске DMA-бенчмарка (большой блок + перекрытие write/read потоками) — BSOD.
- Дамп: `C:\Windows\MEMORY.DMP` (2009 МБ) + миндамп `101726-37171` (пустой) 17.10 09:30.
- **BugCheck 0x10D, Arg1=4** («NULL-параметр») — Probably caused by **`XDMA_DMA!EvtCancelDma+42`**.
- Стек: `EvtCancelDma → WdfDmaTransactionRelease/RequestComplete → FxVerifierNullBugCheck → KeBugCheckEx`. PROCESS_NAME= python.exe.

## 2. Причина
`EvtCancelDma` при отмене выполнял повторный `WdfDmaTransactionRelease` + `WdfRequestComplete`,
когда транзакция УЖЕ обработана `EngineProcessTransfer` (DmaCompleted/Release/Complete) —
двойная обработка освобождённой транзакции → KMDF Verifier (пустой/двойной, 0x10D Arg1=4).
Возникло при перекрывающихся W/R и/или большой транзакции. Имеет место на НЕАКТИВИРОВАННОМ
старом драйвере (без фикса txnDone; перезагрузка не выполнялась).

## 3. Фикс
`xdma_driver_win_src_2017/sys/file_io.c` — `EvtCancelDma`: если `engine->txnDone` уже TRUE
(транзакция завершена), выходим без повторного Release/Complete. Компиляция OK.

## 6. Повторный BSOD после активации фикса #2 (EvtCancelDma) — 17.10 15:27
- Дамп `101726-42171`, **0x10D_4**, `XDMA_DMA!EvtCancelDma+4d`.
- Причина глубже: драйвер использует **ОДИН `dmaTransaction` на движок**. При параллельном
  W+R (перекрывающие потоки) следующий запрос перезаписывает транзакцию раньше, чем
  отменяется старый → cancel старого request трогает чужую/освобождённую транзакцию.
- **Фикс #3**: в `EvtCancelDma` проверять, что активная транзакция движка относится к
  ЭТОМУ request (`WdfDmaTransactionGetRequest(dmaTransaction) != request` → return).
  Компиляция OK. Требует пересборки/установки + ребут.

## 7. Архитектурное ограничение (важно для бенчмарка)
Параллельный W+R на ОДНОМ канале **не поддерживается** архитектурой (один
`dmaTransaction` на движок + KMDF Driver Verifier). Честная максимальная DMA:
**серийный большой блок** (1 MiB) ≈ **250«270 MB/s** (write) / **223«250 MB/s** (read) —
это потолок одиночного канала на этой плате/стеке. Перекрытие для роста MB/s требует
структурной доработки (раздельные транзакции на поток/ус)** = отдельная большая задача.
Вывод: тест `bench_dma.py` с параллельными потоками некорректен для текущего драйвера —
использовать серийные большие блоки.
