# DEVPROG — устройственный секвенсор поверх ring tdot (черновик, 2026-10-20)

## 1. Зачем
Сегодня каждый dot = host-IOCTL ~15 мс (BUG-071). fix: пусть плата держит веса
резидентными и сама прогоняет целую «программу» (данные + список слоёв с повторами и
strides), а хост вмешивается только на границе батча (1 DMA данных + 1 запись программы +
1 чтение completion). Принцип — openTPU (программа в DRAM, LOOP, ARG0..7+RUN, WAITW).

## 2. Модель данных
- Поверх ring (256/1024 задач) вводим ПРОГРАММУ: массив «юнитов» в DDR.
- Юнит (32 Б): { w_addr, n_in, n_out, pass, src(prev|data), out_addr, b_addr, b_en, relu, tag }.
- Интерпретация: for each unit: for p in range(pass): GEMM(data или out_prev) -> out_unit;
  промежуточный out_unit становится входом следующего юнита (или данных при src=data).
- Веса/смещения — резидентны; батч данных — один DMA.
- Завершение: движок пишет status-слово в DRAM-mailbox; host читает 1 слово (WAITW-аналог).

## 3. Отображение на tdot
- tdot умеет dot(x, w) по элементам. Линейный слой = per-output-neuron dot(input, w_col).
  Юнит СЕМАНТИЧЕСКИ = openTPU-дескриптор/SEQ: это «что вычислить», а не «какие биты слать».
- Ринг с кольцом 1024 уже вмещает сотни dot-задач; программа делает то же, но host не
  участвует в каждой задаче — он ждёт ОДНО завершение всей программы.

## 3a. Бюджет DDR3 (256 МБ) — важно!
У нас НЕ 4 ГиБ, а 256 МБ DDR3 (один канал DDR3-800 16-бит). Это меняет правила размещения:
- Резидентные веса: только веса МОДЕЛИ (для аудио-MLP с HIDDEN<=256 это десятки-сотни КБ —
  с большим запасом). Никакого «цифрового» предзагруза всех данных.
- Батч данных: по одному батчу за раз (для аудио 64-4096 сэмплов x 2 признака — тривиально).
- Пока на плате НЕЛЬЗЯ резервировать десятки МБ под таблицы/слои: модель, что не влезает,
  должна грузиться по частям (страницами слоёв), но это уже выходит за текущую аудио-задачу.
- Оценка: даже 4 слоя x 256 скрытых = ~256 КБ весов — ок в 256 МБ; загрузка такого блока
  по PCIe Gen2 x4 (~1.6-2.6 ГБ/с) — доли секунды, разовая.
- Вывод: для НАШЕЙ задачи бюджет не мешает — но дизайн юнита обязан считать размещение
  (адреса в DDR) из программы, а не хардкодить большие резидентные регионы.

## 3b. Completion mailbox (WAITW-аналог) — host-инфраструктура

Адрес синхронизации «на батч»: движок сам пишет статус-слово в DRAM-mailbox,
host ждёт ОДНО слово в конце батча вместо per-task поллинга RPTR/IRQ (это и есть
фикс долгих ~15 мс host-IOCTL, см. §1).

**Расположение** (docs/ADDRESS_MAP.md §6): смещение `0x0012_0000` от
`0x8000_0000` — свободный промежуток DDR3 между областью завершений
(кончается на `0x0011_4000`) и регионом data планировщика (`0x0020_0000`),
в стороне от desc/comp/result/selftest(`0x0100_0000`). Слоты `MAILBOX_STRIDE=0x10`:

| Смещение | Слот | Кто пишет | Назначение |
|---|---|---|---|
| `+0x00` | flag | host | Флаг «готовности»/вооружения батча (host пишет через `write_flag`; движок может читать как подтверждение arming, но не обязан) |
| `+0x08` | status | **движок (RTL)** | Статус-слово завершения батча. `0x0` = свободно (движок ещё не писал); `0x1` (`MAILBOX_STATUS_DONE`) = батч обработан, результаты валидны |

**Формат статус-слова**: одно 64-битное слово в DDR3, значим LSW (первое
4-байтное слово LE). Расширение смысла: старшие биты/слова можно резервировать
под код ошибки, число обработанных задач, номер батча — пока используется
только условие «ненулевое == DONE».

**Протокол ожидания (host)**: `CompletionMailbox` в
`pytorch_layer/xdma_driver.py`:
- `write_flag(word)` — host пишет флаг готовности в слот `+0x00` (через
  `write_dma`), сигнализируя, что параметры/данные батча выложены;
- `read_status(addr, timeout_ms, expected)` — host поллит слот статуса через
  `read_dma(addr, 8)` (один c2h-read слова, извлечение LSW) с шагом ~200 мкс до
  совпадения с `expected` (или появления ненулевого при `expected=0`), до
  таймаута. Возвращает прочитанное слово статуса.

**Что движок будет писать (заглушка для RTL, п.2/4)**: после полной обработки
батча движок выполняет один AXI-write в адрес `DDR3_BASE + MAILBOX_OFF + 8`
с LSW=`MAILBOX_STATUS_DONE` (0x1). До этого RTL статус-слово не трогает
(остаётся `0x0`), поэтому host-таймаут — честный признак незавершившегося батча.

**Валидация на текущей плате** (движок ещё не пишет): `scripts/mailbox_check.py`
сам пишет слово в слот статуса через `write_dma` и читает его через `read_status`
(round-trip канала чтения), плюс проверяет отсутствие пересечения адреса с
desc/comp/data/selftest и корректный таймаут на свободном слоте.

## 6. RTL-модуль `device_prog` (2026-10-21)
Файл: `rtl/integration/device_prog.sv` — САМОДОСТАТОЧНЫЙ интерпретатор «программы
юнитов» поверх кольца tdot. НЕ связан с `tdot_axi4.sv` (интеграция — отдельный шаг).
Модуль по таблицам юнитов в «DDR» выдаёт последовательность «намерений» dot-задач
(`desc_task_*`) — какие задачи поставить в кольцо, и по завершении пишет
completion-mailbox (16 Б статуса). Читает юниты через интерфейс `table_req/rvalid/rdata`
(на интеграции за ним будет DMA/AXI-чтение DDR; в TB — синхронная память).

### 6.1 Параметры и интерфейс
- Параметры: `DEVPROG_EN` (0/1, default 0), `NUM_MAC`, `ADDR_WIDTH`,
  `TABLE_BASE`, `MAILBOX_BASE`, `UNIT_BYTES` (32), `ELEM_BYTES` (8).
  При `DEVPROG_EN=0` модуль ПУСТ: все выходы 0, FSM нет, предупреждений о
  неиспользуемой логике нет — поведение битстрима не меняется.
- Вход stdin-управления: `clk, rst_n, en, go, data_base, table_base,
  mailbox_base, n_units`.
- Выходы-намерения задачи: `desc_task_valid, desc_task_a (data), desc_task_w
  (weights), desc_task_r (result), desc_task_n (n_total=n_in), desc_task_tag`.
- Чтение таблицы: `table_req, table_addr / table_rvalid, table_rdata`.
- Завершение: `done, mailbox_wr_start, mailbox_wr_addr, mailbox_wr_data`.

### 6.2 Формат юнита (32 Б = 4×64b, хвост-адресация в DDR)
```
+0x00 W0  w_addr[63:0]            базовый адрес весов слоя
+0x08 W1  out_addr[63:0]          базовый адрес результата слоя
+0x10 W2  {n_in[15:0], b_addr[47:0]}
+0x18 W3  n_out[15:0] | pass[15:0] | flags[7:0] | tag[15:0] | reserved[7:0]
```
flags: bit0=relu, bit1=b_en, bit2=src (0=data→`data_base`, 1=prev→out_addr предыдущего юнита).

### 6.3 Логика интерпретации (вложенность циклов ≤ 4)
```
for u in [0, n_units):                          // L1 список юнитов
  вход0 = (src==data) ? data_base : prev_out
  for k in [0, pass):                           // L2 проход слоя (pass≥1)
    вход = (k==0) ? вход0 : out_addr            // feed-forward повторы
    for j in [0, n_out):                        // L3 нейроны
      emit desc_task: a=вход, w=w_addr+j*n_in*8,
                      r=out_addr+j*8, n=n_in, tag=tag
  prev_out = out_addr
```
(L4 зарезервирован под батч/внешний LOOP на интеграции.)

### 6.4 Mailbox (16 Б статуса по mailbox_base)
```
+0x00  {48'h0, tag[15:0]}        tag последнего юнита = tag программы
+0x08  {40'h0, units[15:0], status[7:0]}   status: 0 = OK
```
`mailbox_wr_start` пульсирует по слову (addr = base / base+8); AXI-транзакцию делает
интеграция. (См. §3b device-ISA на host: WAITW читает одно status-слово — на интеграции
согласовать семантику «0=OK против nonzero==DONE», см. аудit#4.)

### 6.5 Ключевые решения / gotchas
- Декодирование юнита вынесено в отдельное состояние `ST_DECODE` ПОСЛЕ записи всех
  4 слов: reading `uw[3]` в том же такте, что и его запись (NB), вернул бы устаревшее
  значение (реальный баг, пойман при симуляции).
- Первый запрос таблицы выдается из `ST_FETCH` по уже обнулённым `u_idx/fetch_cnt`,
  а НЕ из `ST_IDLE` — иначе на повторном `go` (после `done`) fetch_addr читался по
  СТАРЫМ индексам и портил `uw[0]` первого юнита (аудit#1, покрыт двух-прогонным TB).
- `desc_task_valid` — 1 задача/такт без готовности (backpressure отсутствует; на
  интеграции поставить FIFO/valid-ready).

`2:[02000|05000|06000|4|BB] 3:[02000|05020|06008|4|BB] 4:[02000|05040|06010|4|BB]` (u1 p0, вход=prev=0x2000)

### 6.7 Не сделано / риск (готово для интеграции)
- НЕ связан с `tdot_axi4.sv` / кольцом (desc_task_* пока не подаются в планировщик).
- НЕ читает DDR сам (таблица — через `table_*`; на плате подключить DMA/AXI).
- Нет backpressure на `desc_task_valid` (нужен FIFO/valid-ready на интеграции).
- Нет аудита малой конфигурации (`n_out=0` → бесконечный цикл; `UNIT_BYTES`-параметр
  зашит как 32 в смещении fetch; семантика mailbox «0=OK vs nonzero==DONE» не согласована
  с host-стороной) — см. аудit#2,4,5 в отчёте.
- Синтез/прошивка ЗАПРЕЩЕНЫ на этом шаге; тестировалось только xvlog/xelab/xsim.
- Точка интеграции с tdot: подать `desc_task_{a,w,r,n,tag}` + `desc_task_valid` на вход
  планировщика кольца (в `tdot_axi4.sv` это выборка дескриптора \(CS_FETCH_DESC /
  CS_SCHED_KICK\): готовые поля адресов/n_total/tag ставятся прямо в кольцо вместо
  чтения дескриптора из DDR, либо через отдельный FIFO к sched движку); mailbox —
  в `COMP_BASE`/mailbox-область, `done`/`mailbox_wr_*` — microblaze/APB. Отдельный
  шаг интеграции НЕ трогает существующую логику dot/кольца (DEVPROG_EN=0 = off).
